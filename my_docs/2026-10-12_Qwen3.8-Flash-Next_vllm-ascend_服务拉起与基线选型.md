# Qwen3.8-Flash-Next 在 vLLM-Ascend 上的服务拉起与基线选型

## 摘要

> Qwen3.8-Flash-Next（`model_type=qwen4_exp`）在 vLLM-Ascend 上的支持尚未合入 main，官方部署文档描述的又是另一套已被取代的实现，照抄其启动命令**必然失败**。本文确定可用基线为 **nightly-main-a3-openeuler 镜像 + main `ea01a44ba` + PR #16981 `c6d9e38f8`**（merge 零冲突，镜像自带的 vLLM v0.30.0 恰好满足该 PR 的依赖），并给出一组与官方文档有三处关键偏离的启动参数。
>
> 实测结果：**A3 单机 TP8 真权重启动成功、精度正常**，decode 约 2 token/s（`--enforce-eager` 且无 MTP 的预期值）。代价是放弃原生 MTP —— MTP 层的 QSA raw cache 宽度与主模型层不同，会触发 six-region 布局的一致性检查。
>
> 本文只覆盖「把服务拉起来」：基线选型依据、零编译路径、启动参数的每处偏离及其证据、环境层面的三个陷阱。hidden 抓取的接口实现与调试记录见[《hidden 抓取适配与 debug 全记录》](2026-10-12_Qwen3.8-Flash-Next_hidden抓取适配与debug.md)，可执行命令见[《穿刺操作手册》](2026-10-12_Qwen3.8-Flash-Next_vllm-ascend穿刺_操作手册.md)。原生 MTP 基线（k=3/k=4 接受长度与吞吐）**尚未取得**，阻塞原因见第 5 节。

## 1. 背景

### 1.1 模型结构带来的约束

Qwen3.8-Flash-Next 的语言模型是混合架构，这决定了它在 vLLM 里要同时满足多套 KV cache 契约：

| 结构 | 规格 | 对 KV cache 的影响 |
|---|---|---|
| 层数 | 48 层，hidden 2560 | — |
| GDN : QSA | 3 : 1，全注意力（QSA）在第 3, 7, …, 47 层（12 层） | 需要 attention + mamba 两类 spec 共存 |
| QSA 稀疏注意力 | `compress_ratio=4`、`token_topk=2048` | 引入 `MLAAttentionSpec`（compressed）和 `CircularBufferSpec`（raw ring）两种额外 spec |
| 残差 | 4 路 hyper-connection（`hc_count=4`），**无 final norm** | 层间状态是 4×2560，lm_head 输入由 `hyper_connection_mixer` 收敛 |
| MoE | 512 专家 × 640，top-10，外加 sigmoid 门控共享专家 | 权重侧显存大头 |
| PLE | 第 1 层 n-gram 表，BF16 约 95 GiB | TP8 下每卡约 11.9 GiB，挤占 KV 预算 |
| MTP | 1 层 | 其 QSA raw cache 宽度与主模型层**不同**，见第 4.3 节 |

权重为 W8A8（个人 msmodelslim 分支 `code_mingming/master-qwen38`@`a3664d45` 导出）：只量化路由专家与 QSA 注意力投影，其余 BF16 透传，无 QuaRot 等旋转。

### 1.2 核心约束：上游支持分散在多个未合入的 PR 里

这是本次选型的主要困难。实测核查结果：

| 核查项 | 结果 |
|---|---|
| main (`ea01a44ba`) 上 `vllm_ascend/models/qwen4_exp/` | **0 个文件** |
| main 上 `envs.py` 的 QSA 相关变量 | **0 个** |
| main 上 `hardware_profile.py` 的 QSA capability | **0 个** |
| main 上与本模型相关的内容 | **仅一份部署文档**（`docs/source/tutorials/models/Qwen3.8-Flash-Next.md`，PR #17024，2026-09-22 合入） |

也就是说 **main 有文档但没有实现**。支持分散在至少 6 个 OPEN PR 中：#16981、#17762（draft）、#15072、#15076、#15162、#17249，另有 #17144 提供 six-region KV 布局、#18159 提供测试。

### 1.3 候选路线对比

| 方案 | 核心机制 | 优势 | 代价 / 限制 | 本文角色 |
|---|---|---|---|---|
| 官方镜像 `qwen3.8-next-a3` | 把上游模型代码 vendor 进插件 | **唯一有公开精度数字**（GPQA-Diamond 91.4） | 2026-09-17 构建，当时 `VLLM_TAG=v0.28.0`，镜像内 vLLM **不含** Qwen4Exp；源码对不上任何公开 commit | 否决，见 1.4 |
| **main + PR #16981** | 复用上游 `vllm.models.qwen4_exp.amd` | 基线可追溯；改动能迁回 main；模型代码由上游维护 | 作者声明 rebase 后未重跑 NPU 端到端；继承了未合入的 #17144 | **采用** |

| PR #17249 | ModelRunnerV2 适配 | — | #16981 明确声明 V1 only，两者不兼容 | 未评估 |

### 1.4 为什么否决官方镜像：两套架构互斥

决定性证据是 vLLM 各 release tag 里 `vllm/models/qwen4_exp/` 的存在情况：

| vLLM tag | 切分日期 | `qwen4_exp` 文件数 | `amd/` 子包 |
|---|---|---|---|
| v0.28.0 | 2026-08-24 | **0** | 0 |
| v0.29.0 | 2026-09-08 | 31 | 12 |
| v0.30.0 | 2026-09-21 | 34 | 12 |

Qwen4Exp 于 2026-08-31 由 [vllm#53896](https://github.com/vllm-project/vllm/pull/53896) 进入上游，v0.28.0 切分在此之前。

再对照 vllm-ascend `Dockerfile.a3` 的 `VLLM_TAG` 变更史：

| 生效日期 | `VLLM_TAG` | 触发 commit |
|---|---|---|
| 2026-09-08 | v0.28.0 | #14898 |
| 2026-09-21 | v0.29.0 | #17004 |
| **2026-09-23 起至今** | **v0.30.0** | #16527（main2main） |

官方 `qwen3.8-next-a3` 镜像构建于 **2026-09-17**（quay.io API 查询），当时 pin 的是 v0.28.0 —— **镜像内的 vLLM 不含 Qwen4Exp**。因此该镜像的模型支持只能走「把上游模型代码拷进 vllm-ascend」的路线（#15162/#15072 的做法），与 #16981 的「复用上游」在架构上**互斥**，无法在它上面叠 #16981 的补丁。

同一条逻辑也解释了官方文档为何不可照抄：文档第 9 行自述基于 **vLLM-Ascend 0.26.0rc**，而 `releases/v0.26.0rc` 分支里 `qwen4_exp` 文件数为 **0** —— 它描述的是又一套不同的实现。

### 1.5 PR #16981 的依赖顾虑已过时

PR 描述中写道「当前 release-tag pairing 基于 vLLM v0.28，不含该上游模型 owner，landing 时需注意此依赖边界」。该顾虑在当前 main 上**已不成立**：main 自 #16527（09-23）起 pin v0.30.0，而 v0.30.0 自带完整的 `qwen4_exp/amd`（12 个文件，正是 #16981 import 的目标）。

实测确认（镜像内）：

```

upstream Qwen4Exp amd OK          # import vllm.models.qwen4_exp.amd.model 成功
```

**结论：版本配对天然成立，无需额外 pin vLLM。**

## 2. 目标与挑战

**成功条件**：A3 单机 TP8 用 W8A8 权重把服务拉起来，发出的 chat 请求返回合理内容（精度正常），并记录可复现的启动命令与 commit。

主要挑战：

1. **基线不存在**：没有任何「拉下来就能跑」的组合。main 缺实现、官方镜像架构互斥、各 PR 互不兼容。需要自己组合并验证。
2. **PR 自身未经真机验证**：#16981 作者明确声明 rebase 后未重跑 NPU 端到端；它继承的 #17144（six-region KV 布局）本身也未合入 main、无人工 review。实际遭遇 3 个启动期阻塞（第 4 节）。
3. **显存紧张且放大机制非直觉**：PLE 表 95 GiB + MoE 512 专家，TP8 下 KV 预算只剩约 11.8 GiB；而 capture 模式下每 token 的 KV 成本被放大到 4.576 MiB（见 debug 文档）。

### 本文主要工作与结果

1. **确定并验证基线组合**：main `ea01a44ba` + PR #16981 `c6d9e38f8`，merge **零冲突**；镜像内 vLLM v0.30.0 满足依赖，实测 import 通过。
2. **确立零编译路径**：核查 PR 的 C++ 改动**仅 1 处**（新算子 `qsa_expand_e3`），`VLLM_ASCEND_ENABLE_QSA_E3V=0` 即可完全复用镜像预编产物，省去 42 个算子的编译，且不影响数值。
3. **真权重启动成功、精度正常**：这是 dummy 权重无法覆盖的部分（PLE 分片、量化 scale、checkpoint key 映射均正确）。
4. **定位启动命令必须偏离官方文档的三处**，每处给出代码级证据（第 3.3 节）。
5. **发现并纠正官方文档的一处错误**：`--speculative-config` 的 method 名。

### 3.2 零编译路径

**PR #16981 对 C++ 的全部改动只有新算子 `qsa_expand_e3`**：

- `csrc/torch_binding.cpp`：1 个 include + 1 个 `qsa_expand_e3_out` 注册
- `csrc/torch_binding_meta.cpp`：1 个 meta 函数 + 1 个注册

别无其他 C++ 改动。因此镜像预编的 `vllm_ascend_C` 与 41 个算子已足够，只要放弃 E3：

| `use_e3` | 走的实现 | 需要新算子 |
|---|---|---|
| `True` | `expand_qsa_block_indices_e3` | 是 |
| `False` | `expand_qsa_block_indices_npu` | 否 |

`use_e3` 只控制最后一步 block→token 索引展开，两条路径输出同一组 token 索引。**Lightning Indexer 本体用 `torch.ops.npu.npu_lightning_indexer`（CANN 原生算子，非 vllm-ascend 自编）**，不受影响。

支撑「放弃 E3 是设计内行为」的三条证据：

1. `vllm_ascend/envs.py` 中 `VLLM_ASCEND_ENABLE_QSA_E3V` 的**默认值本来就是 0**
2. `tests/ut/models/test_qwen4_exp_soc_gating.py:75-82` 有专门 UT 覆盖「capability 缺失 → 退到 triton 且 `use_e3=False`」
3. 官方文档在启动命令里显式 `=1`，把它当性能优化而非必需项

实测验证结果：

```
_cann_ops_custom/ : vendors, 46M
npu_lightning_indexer : True
qsa_expand_e3_out     : False      # 预期如此：_C_ascend 已加载，只缺这一个 op
```

> **踩过的坑**：曾尝试完整编译 42 个算子。首次失败是因为 `OMP_NUM_THREADS=1` 把并行度压成 1，第三方 protobuf 单独编了 **1277 秒**后 ninja 失败，真实报错未取到。既然零编译可行且不影响数值，未再尝试。

另需注意：`hardware_profile` 会报 `QSA_E3_EXPAND = True`，那是**硬件**能力，不代表算子已编译。必须显式设 `VLLM_ASCEND_ENABLE_QSA_E3V=0`，否则运行时会去找不存在的算子。

### 3.3 启动参数：必须偏离官方文档的三处

| 参数 | 官方文档 | 本基线必须 | 证据 |
|---|---|---|---|
| `--block-size` | 不设 | **768** | six-region 要求 `block_size == max_ssm_bytes / k_token_bytes`（`six_region_kv_cache_layout.py:231`）且 `% 128 == 0`（`patch_kv_cache_utils.py:769`） |
| `--speculative-config` | 有（MTP k=3） | **不开** | MTP 层 QSA raw cache `head_size=140` ≠ 主模型层 128，触发 page 一致性检查（详见 debug 文档 4.3） |
| graph | `FULL_DECODE_ONLY` | **`--enforce-eager`** | 无 MTP 的 graph 路径需上游 [vllm#58040](https://github.com/vllm-project/vllm/pull/58040)，该修复未包含在 #16981 中（PR 描述自述） |

另外三处非强制但建议的调整：

- `--language-model-only`：只做文本，跳过 vision encoder 省显存。官方文档说明该开关安全。
- `--gpu-memory-utilization 0.93`：PR #15162 的实战笔记记录 **0.95 会导致 QSA cache 空间不足**，0.93 是其验证值。
- `--max-num-seqs 4`：显存紧张时的保守值。

完整可执行命令见操作手册第 4 节。

### 3.4 官方文档的 MTP method 名是错的

官方文档写 `"method":"qwen3_5_mtp"`，**对本模型不正确**。证据链：

`vllm/config/speculative.py:832`
```python
if hf_config.model_type in {"qwen4_exp", "qwen4_exp_text"}:
    hf_config.model_type = "qwen4_exp_mtp"
```

本模型 `model_type` 即 `qwen4_exp`，映射到 `qwen4_exp_mtp`；而 `qwen3_5_mtp` 那条分支只接受 `qwen3_5` / `qwen3_5_moe` / `qwen3_5_text` / `qwen3_5_moe_text`。

vllm-ascend 侧 `spec_decode/__init__.py:56` 的 proposer 判定同样认 `qwen4_exp_mtp`。PR #15162 与 #17249 的文档都写对了，**只有合入 main 的那份是错的**。

> 补充机制：`speculative.py:1121-1125` 会把所有 `MTPModelTypes`（含 `qwen4_exp_mtp`、`qwen3_5_mtp`）统一改写成 `"mtp"`，所以两者都能通过 Qwen4Exp 的 speculative 白名单。但 proposer 选择基于 draft config 的 `model_type` 而非 `method`，故名字仍须写对。

## 4. 环境层面的三个陷阱

这三个都造成了实际的排查损耗，且都不是代码问题。

### 4.1 `nproc` 返回 1，但 CPU 从未受限

**现象**：容器内 `nproc` 返回 1，`taskset -c 0-639 nproc` 仍返回 1。

**排查弯路**：据此推断是 cgroup cpuset 限制，花了一轮去查 `cpuset.cpus.effective`、`cpu.max` 并准备带 `--cpuset-cpus` 重起容器。该推断是错的 —— 若真是 cgroup 限制，`sched_getaffinity` 也会返回 1。

**根因**：`nproc` 会读 `OMP_NUM_THREADS` / `OMP_THREAD_LIMIT` 并以其为上限（gnulib 的 `NPROC_CURRENT_OVERRIDABLE` 行为）。本机设了 `OMP_NUM_THREADS=1`。

**验证**：

```
printenv OMP_NUM_THREADS            → 1
env -u OMP_NUM_THREADS nproc        → 640
os.sched_getaffinity(0)             → 640      # cgroup 与亲和性从未受限
```

**处置**：编译时必须 `env -u OMP_NUM_THREADS -u OMP_THREAD_LIMIT`，否则并行度被压成 1（protobuf 1277 秒即由此而来）。

### 4.2 权重路径

权重在 `/opt/model/Qwen3.8-Flash-Next-w8a8-mtp`。容器挂的是宿主的 `/opt`，宿主路径 `/dpc/hot/x00873006/...` 在容器内**不可见**。早期按一份未采用的挂载方案写成 `/models/...`，导致一轮「权重看不见」的排查。

### 4.3 `/opt` 下有其他人的工作区

`/opt/w00498770`、`/opt/t828158` 等目录属于同事，其中的 `.so` 是 `cpython-311` 编译的，与本容器的 Python 3.12 不匹配。查找 `vllm_ascend_C*.so` 时会命中这些路径，**勿误用、勿写入**。

## 5. 实测结果与当前边界

### 5.1 真权重启动结果

| 项 | 结果 | 口径 |
|---|---|---|
| 启动 | ✅ 成功 | A3 TP8/DP1，W8A8 真权重，无 MTP，`--block-size 768`，`--enforce-eager`，零编译 |
| 精度 | ✅ 正常 | chat 请求返回合理内容（未跑标准评测集） |
| decode 吞吐 | ⚠️ **约 2 token/s** | 同上配置，单请求 |

**关于 2 token/s**：这是 `--enforce-eager` 叠加无 MTP 的预期值 —— eager 下每步 decode 都要 Python 逐个调度 48 层 + 512 专家 MoE + GDN/QSA 混合的大量小 kernel。该数字**不能**与官方文档的性能数据比较（后者开 ACL Graph 和 MTP k=3）。

对后续 hidden 抓取的影响很小：抓取走 `max_tokens=1` 的纯 prefill，吞吐取决于 prefill 的 batch 并行，与 decode 速度基本无关。

**精度正常是一个重要信号**：它确认了 W8A8 的 checkpoint key 映射、PLE embedding 分片、量化 scale 全部正确 —— 这些恰是 `--load-format dummy` **不校验**的部分（PR #15162 文档明示）。

### 5.2 尚未取得：原生 MTP 基线

穿刺原计划要求记录 MTP k=3 / k=4 的平均接受长度与吞吐，作为后续草稿模型的对照。**当前无法取得**，阻塞于 MTP 层 QSA raw cache 宽度与主模型层不一致（`head_size` 140 vs 128）触发的 six-region page 一致性检查。详见 debug 文档第 4.3 节，其中给出了一个候选修法（fallback 到通用分配器），但**未验证**。

这不阻塞 hidden 抓取（抓取不需要 MTP），但会延后草稿模型的对照评测。

### 5.3 本节结论的适用边界

- 只在 **Atlas 800 A3 + TP8 + 该份 W8A8 权重**上验证。A2 未验证；官方文档明确声明 A2 与 950 系列暂不支持。
- 「精度正常」仅指 chat 请求返回合理内容，**未跑** GPQA 等标准评测集，不能与官方的 91.4 比较。
- decode 吞吐是 eager + 无 MTP 的值，不代表该模型在 A3 上的性能水平。
- 基线组合依赖两个 OPEN PR（#16981 及其继承的 #17144），两者都可能变动。

## 6. 总结与展望

### 已证实的结论

1. **可用基线是 nightly-main-a3-openeuler 镜像 + main `ea01a44ba` + PR #16981 `c6d9e38f8`**，merge 零冲突，镜像内 vLLM v0.30.0 满足依赖（实测 import 通过）。
2. **官方镜像与该基线架构互斥**，官方部署文档描述的是另一套实现（基于 0.26.0rc，该分支 `qwen4_exp` 文件数为 0），其启动命令不可照抄。
3. **零编译可行**：PR 的 C++ 改动仅 1 处新算子，`VLLM_ASCEND_ENABLE_QSA_E3V=0` 下完全复用镜像预编产物，功能与数值不受影响。
4. **A3 TP8 真权重启动成功、精度正常**，decode 约 2 token/s（eager + 无 MTP）。
5. 启动命令相对官方文档有三处必须偏离，每处都有代码级证据；另纠正官方文档中 MTP method 名的一处错误。

# DSpark(MRV2) 接受率比 MTP 高、输出 token 更少，却没有更快 —— 白盒分析报告

日期：2026-08-12
分支：`mrv2_vocab_mapping_inference`
HEAD：`8b178d734`
数据集：MT-Bench 中文版 80 题，投机步数 N = 7
分析范围：MRV2（model runner v2）DSpark 路径，纯代码白盒 + 上游 PR 检索，**没有在设备上实测**

---

## 0. 先把这组数字算清楚

| | MTP | DSpark | 差 |
|---|---|---|---|
| 7 步平均接受率 | 41% | 45% | +4pt |
| 平均 decode token | 628 | 617 | −1.8% |
| TPOT (ms) | 17.537 | 17.798 | +1.5% |
| e2e (ms) | 230975 | 233627 | +1.1% |

由接受率反推每步接受长度 `L = 1 + N × rate`：

```
L(mtp)    = 1 + 7 × 0.41 = 3.87 token/step
L(dspark) = 1 + 7 × 0.45 = 4.15 token/step        (+7.2%)
```

再反推 decode 步数和每步耗时（`每步耗时 = TPOT × L`）：

| | MTP | DSpark | 差 |
|---|---|---|---|
| 每步接受长度 | 3.87 | 4.15 | **+7.2%** |
| decode 步数（628/617 token） | 162.3 | 148.7 | **−8.4%** |
| **每个 decode step 耗时** | **67.9 ms** | **73.9 ms** | **+8.8%** |
| 单请求 decode 总时长 | 11013 ms | 10981 ms | −0.3% |

**结论：接受率这一侧 DSpark 赢了 7~8%，但每个 decode step 贵了 8.8%，两者几乎精确抵消。**
e2e 的 +1.1% 和输出 token 的 −1.8% 都在同量级噪声内（贪心 + 不同生成文本本来就会差几个百分点），
**不必去解释 e2e 的 1.1%，真正要解释的是"每步为什么贵 6 ms"。**

一个重要的量级感：每步 73.9 ms，DSpark 相对 MTP 多出来的是 **约 6.0 ms/step**。
下面所有 finding 都要放在这个 6 ms 的预算里看——单个几十微秒的浪费不解释问题，
毫秒级的同步和串行内核才解释得了。

## 1. 结论（TL;DR）

按"最可能吃掉那 6 ms"排序：

| 级别 | 问题 | 位置 | 是否 DSpark 独有 |
|---|---|---|---|
| **P0-1** | `parallel_drafting` 为真时，**每一次** attention metadata build 都强制 `seq_lens.tolist()`，即一次 D2H 同步；且这个分支对 **target 模型的 build 同样生效** | `attention/attention_v1.py:321,332` | 是（mtp 的 `parallel_drafting=False`） |
| **P0-2** | FULL graph 路径上 draft 的 attention metadata **每步 build 两遍**，第一遍的结果被直接丢弃 —— 等于 P0-1 的同步再翻一倍 | upstream `dflash/speculator.py:385` + `worker/v2/spec_decode/dflash/aclgraph.py:85` | 是（dflash/dspark 共有） |
| **P1-1** | MRV2 专用的 Ascend prepare 内核是**单 program 串行**，且每步用**逐元素标量循环**把 query slot mapping 补到 `max_num_batched_tokens` | `worker/v2/spec_decode/dflash/speculator.py:198,287`（由 `patch/worker/patch_v2/patch_triton.py:34` 装上） | 是 |
| **P1-2** | context K/V 预计算每步 **eager 跑在图外**；Ascend 版本比上游少融合，且 `tmpv = all_k_flat.clone()` 白白把 RoPE 算了两遍 | `patch/worker/patch_qwen3_dflash.py:35-46`；DSV4 版本 `models/deepseek_v4_dspark.py:205-219` 完全没融合 | 是（DFlash 家族独有的结构） |
| **P2-1** | Markov head 每步做 **7 次串行的 vocab 维 all-gather**，MTP 侧可以走 `use_local_argmax_reduction` 绕开 | upstream `dspark/speculator.py:119-149` + `logits_processor._gather_logits` | 是 |
| **P2-2** | confidence head / 动态验证长度没启用，永远固定草 7 验 8 —— DSpark 论文里的主要提速来源没吃到 | `llm_base_proposer.py:1203-1205` 注释 "Not yet achieved" | 是 |
| **A-1** | MRV2 里 padding 请求的 draft `seq_lens` 被写成 **0**；v1 图路径当初专门用 1（`_GRAPH_PADDING_REQUEST_KV_LEN`），理由是 "A padded DSpark request must have a positive KV length for FIA" | `worker/v2/spec_decode/dflash/speculator.py:273,421` | 是 |
| **A-2** | `sample_from_anchor` / draft attention 的 causal 读法可能还是旧的；上游已合的 #13530 证明读错会**明显压低接受率** | 见 §4 | 是 |

精度层面：**本分支的 reduced-vocab 改动（d2t 映射 + 裁剪 lm_head）本身 review 下来是自洽的**，
没有发现会静默出错的地方（细节见 §4.3）。真正值得再看一眼的是 A-1 / A-2 两条。

## 2. DSpark 每步比 MTP 多做了什么（结构对比）

同样是"一个 decode step 产出最多 8 个 token"：

| | MTP（autoregressive speculator） | DSpark（parallel drafting） |
|---|---|---|
| draft forward 次数 | N = 7 次，每次 1 token/req | **1 次**，7 token/req |
| draft 输入准备 | 每步小 kernel | 一次 triton prepare kernel（**串行版**，见 P1-1） |
| context K/V | 不需要 | **每步 eager 预计算并写 cache**（图外） |
| 采样 | 7 次 `compute_logits` + argmax | 1 次 base logits + **7 次串行 Markov 偏置**（每次一发 all-gather） |
| attention metadata | 每步 build，走 host 侧 seq_lens | **每步 build 两遍**，且强制走 device seq_lens → 同步 |
| target 侧 | 只要最后一层 hidden | 还要 `aux_hidden_states` 多层 concat + `main_proj` |
| ACL graph 覆盖 | prefill 步可 PIECEWISE，decode 步需要 FULL | 只有 `cudagraph_mode.decode_mode() == FULL` 才有图，否则**整个 draft 全 eager** |

从"模型计算量"看 DSpark 应该稳赢（1 次 L 层 vs 7 次 1 层，小 batch 下 MoE/权重读取次数才是主项）。
所以 6 ms 大概率**不在模型里，在上面那一列"每步固定开销"里**。这正是下面 findings 的落点。

## 3. Findings（性能）

### [P0-1] `parallel_drafting` 让每一次 attention build 都做一次 D2H 同步

位置：`vllm_ascend/attention/attention_v1.py:305-333`

```python
if common_attn_metadata._seq_lens_cpu is not None:
    seq_lens = common_attn_metadata._seq_lens_cpu[:num_reqs]
elif common_attn_metadata.seq_lens_cpu is not None:
    seq_lens = common_attn_metadata.seq_lens_cpu[:num_reqs]
else:
    seq_lens = common_attn_metadata.seq_lens[:num_reqs].to("cpu")
...
elif self.speculative_config and self.speculative_config.parallel_drafting:
    seq_lens = common_attn_metadata.seq_lens          # ← device tensor
...
seq_lens_list = seq_lens.tolist()                     # ← D2H，阻塞式同步
```

两点：

1. **`.tolist()` 在 device tensor 上是一次全同步。** host 必须等到 draft 的 prepare kernel
   算完 `input_buffers.seq_lens` 才能继续。MRV2 整个设计（optimistic seq lens、
   idx_mapping 全在 device 上算）就是为了让 host 一路跑在 device 前面；这一行把这个性质打掉了。

2. **`self.speculative_config` 是全局的，不是 draft 专属的。**
   `parallel_drafting` 只在 method ∈ {dflash, dspark} 时为 True
   （vLLM `config/speculative.py:910-911`，mtp 恒为 False），
   所以只要开了 DSpark，**target 模型自己的 attention build 也会掉进这个分支**——
   而 target 侧 `seq_lens_cpu` 本来就是权威的 host 镜像，这次同步是纯亏。

   > 适用条件：target 用 `AscendAttentionBackend`（如 Qwen3 系）时命中。
   > target 走 MLA / DSA / SFA（DeepSeek 系）时不命中，因为 `mla_v1.py` / `dsa_v1.py` /
   > `sfa_v1.py` 里没有这个分支。**这是先要确认的第一件事。**

每步同步次数（target 命中 AscendAttentionBackend 的情况）：
target build 1 次 + draft build 2 次（见 P0-2）= **3 次阻塞同步/step**。
在一个 74 ms 的 step 里，这是最有可能装得下 6 ms 的地方。

**修法**：把这个分支限制到 draft builder（`_EXTRA_CTX.is_draft_model` 已经有了），
target 继续用 `seq_lens_cpu`。draft 侧因为 host 根本算不出 `-num_rejected` 后的长度，
同步暂时去不掉，但至少从 3 次降到 2 次；再配合 P0-2 降到 1 次。

### [P0-2] FULL graph 路径上 draft attention metadata 每步 build 两遍

- upstream `vllm/v1/worker/gpu/spec_decode/dflash/speculator.py:383-390`：
  `propose()` 里**无条件**先 build 一次
  （注释写的是 "Rebuild ... even when replaying the FULL graph so that any attention
  metadata builder state is updated"）。
- 然后 `vllm_ascend/worker/v2/spec_decode/dflash/aclgraph.py:85-88`：
  `run_fullgraph()` 里又调 `self.speculator.build_draft_attn_metadatas(...)` build 一次，
  **这一次的结果才真正被 `update_full_graph_params` 用来更新图里的 FIA 参数**。

也就是说 FULL 路径上第一次 build 的产物 `draft_attn_metadata` 完全没有被使用
（只有 `else` 分支里的 `_generate_draft(...)` 会用）。每步白做一遍 metadata 构造，
**外加 P0-1 那次 `.tolist()` 同步**。

**修法**：`propose()` 里当 `batch_desc.cg_mode == CUDAGraphMode.FULL` 时跳过第一次 build。
上游那句注释是为 GPU builder 的内部状态写的，Ascend 这边第二次 build 已经把状态刷新了；
改之前先确认 Ascend builder 没有跨步的增量状态。

### [P1-1] MRV2 的 Ascend prepare 内核是串行的，且每步逐元素补 PAD 到 `max_num_batched_tokens`

位置：`vllm_ascend/worker/v2/spec_decode/dflash/speculator.py`
（`_prepare_dflash_inputs_kernel_ascend`，由 `patch/worker/patch_v2/patch_triton.py:34`
替换掉上游的向量化版本）

上游内核是 `(num_reqs, num_blocks)` 二维并行 + `tl.arange` 向量化：

```python
j = block_idx * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
...
for i in range(q_pad_start, max_num_tokens, BLOCK_SIZE):
    block = i + tl.arange(0, BLOCK_SIZE)
    tl.store(out_query_slot_mapping_ptr + block, PAD_SLOT_ID, mask=block < max_num_tokens)
```

Ascend 替换版（`speculator.py:198` 起）：

```python
if block_idx > 0:
    return                                   # 只有一个 program 干活
for j in range(0, num_ctx):                  # 标量循环
    ...
for q_off in range(0, num_query_per_req):    # 标量循环
    ...
if req_idx == num_reqs - 1:
    ...
    q_pad_start = num_reqs * num_query_per_req
    for i in range(q_pad_start, max_num_tokens):        # ← 逐元素
        tl.store(out_query_slot_mapping_ptr + i, PAD_SLOT_ID)
```

`max_num_tokens = scheduler_config.max_num_batched_tokens`（常见 8192 / 16384）。
decode 时 `q_pad_start = num_reqs × 7`，也就是**每个 decode step 都要用一个 AI core
串行写掉近 8k~16k 个标量 store**。前面几个循环在 decode 下很小（num_ctx = 8/req），
真正的开销全在这个补 PAD 的尾巴上。

而且这个补 PAD 是**过量**的：图回放时只会读到
`block_tables.slot_mappings[gid][:num_tokens_padded]`，而 `num_tokens_padded ≤
max_num_reqs × num_query_per_req`。补到 `max_num_tokens` 是白补的
（`max_num_reqs=16, N=7` 时只需要 112，却补了 8192）。

**旁证**：v1 那条链路上同类问题已有 PR —— vllm-ascend **#13191
"[Performance] Optimized Kernel copy_and_expand_dflash_and_dspark_inputs"**，
描述里明写 "launched with `grid=[1,]` ... 约 47/48 个 vector core 空转 ... 大 context 下
~2.2 ms/call"，优化后 22~28x。**但 #13191 改的是 v1 的
`ops/triton/spec_decode/utils.py`，MRV2 这个内核不在它的覆盖范围里。**

**修法**（按性价比）：
1. 把 `for i in range(q_pad_start, max_num_tokens)` 的上界改成
   `max_num_reqs * num_query_per_req`（或者当前 capture size）—— 一行改动，最大收益；
2. 补 PAD 从 kernel 里挪出来，用一次 host 侧 `slot_mappings[gid][a:b].fill_(PAD_SLOT_ID)`；
3. 参考 #13191 把整个内核改成 grid-stride 并行 + 向量化。

### [P1-2] context K/V 预计算：每步 eager，且比上游少融合

这是 DFlash/DSpark 家族的结构性开销：query block 的 shape 固定所以能进图，
但 context 的 token 数每步都在变，所以 `precompute_and_store_context_kv` **只能在图外 eager 跑**
（upstream `dflash/speculator.py:350-367` 的注释就是这么写的）。MTP 完全没有这一段。

Ascend 这边还比上游更亏：

**(a) Qwen3 路径** —— `vllm_ascend/patch/worker/patch_qwen3_dflash.py`：

```python
# --- Per-layer RMSNorm K ---
all_k_normed = torch.empty_like(all_k)
for i in range(L):                                    # ← 上游是一次 grouped ops.rms_norm
    k_norm_layer = self.layers[i].self_attn.k_norm
    all_k_normed[i] = k_norm_layer(all_k[i])
...
tmpv = all_k_flat.clone()                             # ← 每步多一次 alloc + 全量拷贝
self.layers[0].self_attn.rotary_emb(positions_repeated, all_k_flat, tmpv)
```

- 逐层 `k_norm` + 逐层切片赋值 = `2L` 次额外 kernel launch/step（上游 1 次）；
- `tmpv` 只是为了凑 `rotary_emb(q, k)` 的签名，算完就扔——
  **等于每步多做一次 clone + 一整份 RoPE**（上游那边 key 传的是 `None`）。

**(b) DSV4 路径** —— `vllm_ascend/models/deepseek_v4_dspark.py:205-219`：

```python
for layer_idx, layer in enumerate(self.layers.values()):
    attn = layer.self_attn
    shared_kv = self._project_shared_kv(context_states, context_positions, attn)   # 逐层 GEMM
    self._store_standard_swa_kv(shared_kv, layer_context_slot_mapping, attn)       # 逐层 scatter
```

完全没有融合：L 层就是 L 次 `wkv` GEMM + L 次 norm + L 次 RoPE + L 次 scatter。
上游对 Kimi-K3 做过完全同类的优化 —— vllm **#50585
"[K3 Perf] Optimize k3 dspark fused kv, 4.5~4.6x kernel performance improvement"**，
思路就是把逐层投影融成一次 GEMM。

**修法**：把 `wkv` 权重按层 stack 成一个融合权重，一次 GEMM 出 `[L, num_ctx, ...]`，
一次 RoPE 跑 `L*num_ctx`，只保留逐层 scatter；Qwen3 那边先把 `tmpv` 干掉（零风险）。

### [P2-1] Markov head 每步 7 次串行 vocab 维 all-gather

位置：upstream `vllm/v1/worker/gpu/spec_decode/dspark/speculator.py:119-149`

```python
for i in range(n_spec):                                  # n_spec = 7
    markov_embed = self.model.markov_embed(prev)
    bias = self.model.markov_bias(markov_embed)          # → logits_processor(markov_w2, ...)
    logits_i = base_logits[:, i] + bias
    ...
```

`markov_w2` 是 `ParallelLMHead(draft_vocab_size, markov_rank)`，
`markov_bias` 走 `LogitsProcessor.forward` → `_get_logits` → `_gather_logits`，
即 **每次迭代一发 `tensor_model_parallel_all_gather`，7 次串行**（加上 base logits 共 8 次）。
MTP 一步一发、共 7 次，看似持平，但 MTP 还可以走
`speculative_config.use_local_argmax_reduction`（`spec_decode/speculator.py:255`，
通信从 O(vocab) 降到 O(2·tp_size)），DSpark 这条路走不了——
v1 里甚至直接 `raise NotImplementedError`（`llm_base_proposer.py:1166-1175`）。

**上游已经有对症的 PR**：
- vllm-ascend **#13979 "[Performance][Spec Decode] Replicate DSpark Markov head across TP ranks"**
  （8/11 开，**未合**）：Markov head 本身很轻，TP 切分带来的通信不划算，
  改成每卡各算一份、去掉 all-gather。DeepSeek-V4-Flash / 8×910B 上报 **+2.05% 吞吐**，
  上游 vLLM 侧报 +3.3%~+3.8%。**注意 review 里指出了 `outout_parallel` 拼写和属性访问的错，
  照搬要先修。**
- vllm-ascend **#13724 "[Feature][Spec Decode] Add reduce_sample branch for dspark"**（未合）：
  给 DSpark 补上 reduce_sample 分支，正好填掉上面那个 `NotImplementedError`。

按 +2~4% 的量级，这条**解释不了 6 ms**，但是确定能拿的。

### [P2-2] 没有 confidence-scheduled verification / 动态投机长度

`llm_base_proposer.py:1203-1205` 的注释自己写着：

> The ConfidenceHead predicts the expected acceptance length of tokens **(Not yet achieved)**.

也就是说现在无论上下文好不好草，永远是"草 7 个、验 8 个"。DSpark 原始方案里
"硬件感知的置信度调度验证"才是主要的提速来源——低置信度时缩短验证长度，
把每步固定开销摊薄。相关 PR：

- vllm **#47808 "[Spec Decode] DSpark confidence-scheduled verification"**（7/7 开，**未合**）；
- vllm-ascend **#9620**（dflash 的 EMA 动态投机长度，**卡在冲突 + review**：
  `_last_draft_token_count` 取错对象、热路径上多次同步 D2H）。报告里给的数据是
  batch 64 混合集上 dynamic spec_num=4 达 2357 tok/s vs static 2194 tok/s，e2e 130.5s → 121.5s。

这是中期方向，不是这次调优该先做的。

### [P2-3] draft graph 的 capture size 要 round_up 到 7 的倍数

`cudagraph_utils.py:234`：`rounded_num_tokens = round_up(num_tokens, decode_query_len)`。
DSpark 的 `decode_query_len = num_query_per_req = N = 7`（`sample_from_anchor` 为真时），
MTP 的 draft decode 是 1。所以 DSpark 的 draft 图尺寸都是 7 的倍数，
实际 batch 会被 pad 到下一个 capture size。影响不大（几十个 token），但要知道它存在——
特别是在 `cudagraph_capture_sizes` 稀疏的大尺寸段。

**另外必须先确认的一件事**：`DFlashSpeculator.init_cudagraph_manager`（upstream
`dflash/speculator.py:85-98`）里：

```python
if cudagraph_mode.decode_mode() == CUDAGraphMode.FULL:
    cudagraph_mode = CUDAGraphMode.FULL_DECODE_ONLY
else:
    cudagraph_mode = CUDAGraphMode.NONE       # ← PIECEWISE 直接退化成无图
```

**如果这次跑的是 PIECEWISE，DSpark 的整个 draft（backbone + 7 步 Markov）是全 eager 的，
而 MTP 的第 0 步还有 `PrefillSpeculatorCudaGraphManager` 的 breakable CG 兜着。**
那样的话 6 ms 立刻就有解释了。启动日志里搜 `Capturing dspark CUDA graphs` 能一眼确认。

## 4. Findings（精度 / 接受率）

### [A-1] MRV2 里 padding 请求的 draft `seq_lens` 是 0

`worker/v2/spec_decode/dflash/speculator.py:272-273`（Ascend 版）和上游内核 `:541-542`：

```python
for i in range(num_reqs, max_num_reqs):
    tl.store(out_seq_lens_ptr + i, 0)
```

而 v1 图路径当初专门加过：

```
llm_base_proposer.py:69    _GRAPH_PADDING_REQUEST_KV_LEN = 1
llm_base_proposer.py:2328  padding_value = _GRAPH_PADDING_REQUEST_KV_LEN if self.method == "dspark" else 0
# 注释：A padded DSpark request must have a positive KV length for FIA
```

MRV2 这边没有这个保护。padding 请求的输出本来就会被丢掉，所以**大概率不影响正确性**，
但 FIA 对 `actual_seq_kvlen = 0` 的行为需要确认（v1 当时是踩到过才加的）：
最坏情况是报错或产生 NaN。**未验证**，建议在 padded batch 上跑一次带 NaN 检查的用例。

### [A-2] `sample_from_anchor` 和 draft attention causal 的读法

vllm-ascend **#13530 / #13531 "[BugFix] Fix GLM-5.2 DSpark acceptance rate problem"（已合，8/7）**
说明了一个真实存在的坑：新版 DSpark 权重

1. attention layer type 从 `full_attention` 变成 `sliding_attention`；
2. 新增 `sliding_window_non_causal` 表示 draft 是否用非因果掩码。

修法是两处：`sample_from_anchor` 直接读配置里的同名字段（不再用取反的旧字段
`dspark_bonus_anchor`），`cad.causal` 改成 `self.model.get_draft_attn_causal()[0]`
（不再硬编码 `False`）。修完 GSM8K 上平均接受率提到 51~65%。

本仓库 v1 侧**还是旧读法**：

```
spec_decode/dspark_proposer.py:40   self.sample_from_anchor = not getattr(hf_config, "dspark_bonus_anchor", False)
spec_decode/dspark_proposer.py:295  cad.causal = False
```

MRV2 侧这两个值来自上游 `DSparkSpeculator`（`sample_from_anchor` 同样是
`not getattr(hf_config, "dspark_bonus_anchor", False)`，causal 在旧版是硬编码
`self.dflash_causal = False`；新版上游已经改名成 `_group_causal` 并支持按 KV group 取值，
`AscendDSparkSpeculator.build_draft_attn_metadatas` 里用的就是 `self._group_causal`）。

**所以要确认的是：当前装的 vLLM 里 `_group_causal` 到底从哪读、读出来是什么，
以及这个 checkpoint 的 config 里有没有 `sample_from_anchor` / `sliding_window_non_causal`。**
如果读错，接受率是"能跑但偏低"，45% 完全可能还有空间——#13530 那边修完是 51~65%。
这是本报告里**最可能直接提升接受率的一条**，建议优先确认。

相关的还有 vllm-ascend **#13925 "[BugFix] DeepSeek-V4 DSpark uses non-causal attention by default"**
（已关）和 **#13831/#13935 "Avoid DSpark crash when causality API absent"**（0.26.0 分支已合）。

### [A-3] 本分支的 reduced-vocab 改动：review 结论是自洽的

`spec_decode/vocab_mapping.py` + `worker/v2/spec_decode/dspark/speculator.py:49-70` 全部读过：

- `validate_draft_vocab_mapping` 用"权重流里有没有出现过 d2t"来区分"没加载"和
  "合法地保留了 target id 0..K-1"，这个歧义处理是对的（光看 offset 全零区分不出来）；
- 严格递增 + 越界检查覆盖了"拿错 target 训的 draft"；
- `derive_pruned_lm_head` 用 target head 的 comm_group 做一次
  `draft_vocab_size` 行的 all-reduce 再交给 draft head 自己的 `weight_loader`，
  TP 语义是对的，也支持 `draft_tensor_parallel_size=1` 打 TP target；
- 热路径上：`compute_draft_logits` 出 draft 词表宽的 logits、Markov bias 也是 draft 词表宽、
  两者相加后 argmax、再 `map_draft_to_target` 映回 target id 才喂给 `markov_w1`（`markov_w1`
  是 target 词表宽的）——顺序是对的，映射前后没有错位。

这些**都是 load 时一次性的开销，不在每步热路径上**，跟这次的 6 ms 无关。

### [A-4] 如果用的是 probabilistic 采样，额外注意

`dspark/speculator.py:124-144` 的 reduced-vocab probabilistic 路径每步会做 7 次
`buf.index_copy_(1, self._d2t_scatter_index, logits_i)`，`buf` 是
`[max_num_reqs, vocab_size]` 的 fp32；再叠加 `draft_logits`
`[max_num_reqs, N, vocab_size]` fp32 的写入。词表 150k、32 并发时后者是 134 MB 常驻、
每步写 ~19 MB。**贪心（默认）不走这条路**，但如果这次实验开了 probabilistic，
这本身就是一大块每步开销，要先排掉。

## 6. 建议的验证顺序

**第 0 步（免费，5 分钟）**：确认图模式。启动日志里找

**第 1 步**：确认 P0-1 是否命中 target。

命中 target 就是最高优先级的修改点。

**第 2 步**：一个 decode step 的 profile（`torch_npu.profiler`，抓 5~10 步）。

## 7. 证据强度与未验证项

**代码层面确认（读到了源码，可信）**：
- P0-1 的 `.tolist()` 在 device tensor 上、且 `parallel_drafting` 对 target 也生效；
- P0-2 的两次 build；
- P1-1 内核的串行结构和 pad 上界是 `max_num_batched_tokens`；
- P1-2 的逐层循环与 `tmpv` clone；
- P2-1 的 7 次 `_gather_logits`；
- A-1 的 padding seq_lens = 0；
- A-3 的 reduced-vocab 逻辑正确性。

**推断，未实测（需要 profile 证实）**：
- 上述各项在 6 ms/step 里各占多少。报告里没有给任何一项的实测耗时，
  排序是按"结构上能装下多少毫秒"排的，不是按测量排的；
- P0-1 是否命中 target，取决于 target 用的是哪个 attention backend（见 §3 P0-1 的方框）；
- A-1 的 `seq_lens = 0` 在 FIA 上到底是无害还是会 NaN/报错。

**这次分析没有覆盖**：
- 具体跑的是哪个 target/draft 组合（DSV4-DSpark 还是 Qwen3-DSpark），
  报告对两条路径都给了对应位置，但没法判断哪条生效；
- target 侧 `aux_hidden_states` 的多层 concat + `main_proj` 对 target 图/融合的影响；
- rejection sampler 侧 DSpark 与 MTP 的差异；
- prefill/TTFT（e2e 的 1.1% 里可能有一部分来自这里，本报告只解释了 decode）。

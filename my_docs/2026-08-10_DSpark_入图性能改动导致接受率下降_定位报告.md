# DSpark 入图性能改动导致接受率下降 —— 定位报告

日期：2026-08-10
分支：`0810_dspark_compile`
HEAD：`5042c87cc`
现象：同一 draft model、5 个测试集，平均接受率一致下降 7～8%（投机步数 N = 7）
排查范围：`bdab23475..5042c87cc`（本次入图相关改动），model runner v1 路径

---

## 结论

问题出在 **`5042c87cc "remove copy performance degrade"`**。

这个提交为了去掉 `seq_lens.tolist()` 这次 D2H 同步拷贝，改成从 host 侧镜像 `_seq_lens_cpu` /
`seq_lens_cpu` 读 KV 长度。但在 **parallel drafting（dflash / dspark）路径上这两个 CPU 镜像
从来就不是权威值**：DSpark 的 `set_inputs_first_pass()` 只把 draft 特有的
`-num_rejected + N` 修正写进了 **GPU 上的 `cad.seq_lens`**，没有同步写 CPU 镜像。

于是 FIA 拿到的 `actual_seq_lengths_kv` 变成了 target 的序列长度，比 draft 真正需要的
KV 长度**短了 `N - num_rejected` 个 token**。`sparse_mode=3` 是右对齐因果 band，KV 长度
少 d，等价于**每个 draft query 的注意力窗口整体向前平移 d 个 token**——draft 看不到刚被
target 接受的最新几个 token，只能基于过期上下文出草稿。接受率因此系统性下降。

同一提交还有第二处改动（`llm_base_proposer.py`）把 dspark 从 parallel-draft 分支挪到了
通用分支，在 **full graph 路径上直接用 `self.runner.seq_lens` 覆盖掉了 draft 已经算好的
`cad.seq_lens`**，把同一个信息又丢了一遍，并且顺带回退了 `b952f3519` 引入的
padding 请求 KV 长度必须为正的约束。

`b952f3519 "dspark graph compile"`（8-05，真正的入图使能）和 `501085274`（8-07，graph
dispatch key 修复）在 seq_lens 这条链路上是自洽的，没有发现会导致接受率下降的问题。

**建议：先回滚 `5042c87cc` 的两处改动，重跑一遍 5 个测试集确认接受率回到基线，再讨论怎么
用不破坏语义的方式去掉那次拷贝。**

## 背景：DSpark draft 的 KV 长度是怎么算出来的

`vllm_ascend/spec_decode/dspark_proposer.py:342-347`：

```python
effective_seq_lens = cad.seq_lens
if has_num_rejected:
    effective_seq_lens = effective_seq_lens - num_rejected_tokens_gpu

cad.query_start_loc = self.arange_dflash[: batch_size + 1] * self.num_query_per_req
cad.seq_lens = effective_seq_lens + self.num_query_per_req
```

即：

```
draft_kv_len = target_seq_len - num_rejected + N          (N = num_query_per_req = 7)
```

- `- num_rejected`：上一轮被拒的 draft token 要从 KV 里退掉；
- `+ N`：本轮 draft 自己的 N 个 query token 会先写进 KV，再参与 attention。

注意这里**只改了 `cad.seq_lens`（device tensor）**。`cad.seq_lens_cpu` / `cad._seq_lens_cpu`
原样带的是 target 的值（`llm_base_proposer.py:2280-2282` 透传，值来自
`runner.optimistic_seq_lens_cpu`）。

这不是疏忽。默认走的是 `prepare_inputs_padded()`（`llm_base_proposer.py:2211`），它的
docstring 明写 *"No blocking CPU operations should be introduced in this function"*——
`num_rejected_tokens_gpu` 只存在于 device 上，host 侧根本无法在不同步的前提下算出正确值。

正因如此，attention builder 里原本有一条专门的分支（`df1ee8070` / PR #6766 引入）：

```python
elif self.speculative_config and self.speculative_config.parallel_drafting:
    seq_lens = common_attn_metadata.seq_lens      # 强制用 GPU 上的权威值
...
seq_lens_list = seq_lens.tolist()
```

**这条分支存在的唯一目的，就是在 parallel drafting 下绕开不可信的 CPU 镜像。**
`parallel_drafting` 对 dflash / dspark 恒为 True（vLLM `config/speculative.py:910-911`）。

## Findings

### [P0] `attention_v1.py`：`seq_lens_list` 改读 CPU 镜像，draft 的 KV 窗口整体前移

位置：`vllm_ascend/attention/attention_v1.py:315-336`

```python
seq_lens_cpu_mirror = None
if isinstance(self.kv_cache_spec, CrossAttentionSpec):
    ...
elif self.speculative_config and self.speculative_config.parallel_drafting:
    seq_lens_cpu_mirror = seq_lens          # ← 这里的 seq_lens 还是 CPU 镜像
    seq_lens = common_attn_metadata.seq_lens

...
# seq_lens_list = seq_lens.tolist()
seq_lens_list = (seq_lens if seq_lens_cpu_mirror is None else seq_lens_cpu_mirror).tolist()
```

`seq_lens_cpu_mirror` 取的是函数上方那段（`attention_v1.py:307-313`）算出来的
`_seq_lens_cpu[:num_reqs]` / `seq_lens_cpu[:num_reqs]`，也就是 **target 的长度**。
改完之后：

- `attn_metadata.seq_lens`（tensor）= draft 正确值；
- `attn_metadata.seq_lens_list`（list）= target 值。

两者不再一致，而 FIA 实际吃的是后者：

- eager：`attention_v1.py:1443` / `1473` `actual_seq_lengths_kv=seq_lens_list[...]`，`sparse_mode=3`；
- full graph replay：`attention_v1.py:615` → `attention_v1.py:634` `actual_seq_kvlen=seq_lens`
  （取自 `attn_metadata[draft_step][key].seq_lens_list`），`next_tokens=0`。

**偏差量：**

设 target 侧 optimistic 长度为 `S`，被拒 token 数为 `r`。

| 路径 | 正确 KV 长度 | 实际传给 FIA | 偏差 d |
|---|---|---|---|
| `prepare_inputs_padded`（默认，async） | `S - r + N` | `S`（optimistic，未减 r） | `N - r` |
| `prepare_inputs`（`disable_padded_drafter_batch=True`） | `S' + N`（`S'` 已减 r） | `S'` | `N = 7`（恒定） |
| prefill / 首步（`spec_decode_metadata is None`） | `S + N` | `S` | `N = 7` |

默认路径下 `r = (N + 1) - accepted`，代入得：

```
d = N - r = accepted - 1
```

**这个 bug 恰好惩罚接受得最好的请求**：这一轮接受 1 个 token（全拒）时 `d = 0`，完全不受影响；
接受 8 个（全中）时 `d = 7`，draft 的 attention 窗口整体前移 7 个 token，等于完全看不到自己
这一轮的 query KV，也看不到最后几个刚被接受的 target token。这种"越好越砍"的负反馈会把接受率
压到一个新的、更低的平衡点，且**与数据集无关**——和 5 个测试集一致下降 7～8% 的现象吻合。

`sparse_mode=3` 是 bottom-right 对齐的因果 band：query i 的可见范围是 `[0, kvlen - qlen + i]`。
`kvlen` 少 d，窗口右端就少 d，所以是"平移"而不是单纯"截断尾巴"。

**影响面：dflash 同样中招。** `dflash_proposer.py:132` 也是只改 `cad.seq_lens`
（`cad.seq_lens = effective_seq_lens + num_query_per_req`），不动 CPU 镜像。

### [P0] `llm_base_proposer.py`：full graph 路径把 draft 算好的 seq_lens 覆盖掉

位置：`vllm_ascend/spec_decode/llm_base_proposer.py:1092-1107`

```python
-            if self.method in ("dflash", "dspark"):
-                common_attn_metadata.seq_lens = self._adjust_parallel_draft_seq_lens_for_graph(
-                    common_attn_metadata.seq_lens, num_reqs_padded
-                )
+            if self.method == "dflash":
+                common_attn_metadata.seq_lens = self._adjust_tensor(common_attn_metadata.seq_lens, num_reqs_padded)
             else:
                 common_attn_metadata.seq_lens = self._adjust_tensor(self.runner.seq_lens, num_reqs_padded)
                 common_attn_metadata.seq_lens_cpu = self._adjust_tensor(
                     self.runner.optimistic_seq_lens_cpu, num_reqs_padded
                 )
                 if common_attn_metadata._seq_lens_cpu is not None:
                     common_attn_metadata._seq_lens_cpu = common_attn_metadata.seq_lens_cpu.clone()
```

`set_inputs_first_pass()` 在 `_propose()` 里是先于这段执行的（`llm_base_proposer.py:989`
→ `_prepare_inputs`）。dspark 掉进 `else` 分支后：

1. `cad.seq_lens` 被 `self.runner.seq_lens`（target 值）整个覆盖，`-r + N` 的修正丢失；
2. `cad.seq_lens_cpu` / `_seq_lens_cpu` 被写成 `runner.optimistic_seq_lens_cpu`。

第 2 点让 P0-1 在 graph 路径上"看起来自洽"了——tensor 和 list 现在一致地错。这也是为什么这个
bug 不会以 shape 不匹配或 FIA 报错的形式暴露出来，只会安静地降接受率。

顺带两个回归：

- **padding 请求 KV 长度回到 0。** `b952f3519` 专门加了
  `_GRAPH_PADDING_REQUEST_KV_LEN = 1` 和注释 *"A padded DSpark request must have a positive
  KV length for FIA"*；现在 dspark 不再走 `_adjust_parallel_draft_seq_lens_for_graph()`，
  虚拟请求的 KV 长度变回 0。`attention_v1.py:359-361` 那段补 `[1]` 的兜底在这里不生效
  （`len(seq_lens_list)` 已经等于 `num_reqs_fia`）。只影响 padding 请求本身，**未实测**是否会
  触发 FIA 报错或产生 NaN。
- `_adjust_parallel_draft_seq_lens_for_graph()`（`llm_base_proposer.py:2323`）现在只剩
  dflash 一个调用方，而它内部的 `padding_value` 判断只对 dspark 生效，等于成了死代码。

### [P2] 目标模型侧也受同一改动影响（未验证）

`self.speculative_config` 在 target 的 builder 上同样非空，所以只要开了 dspark/dflash，
**target 模型的 attention build 也会走 `seq_lens_cpu_mirror` 这条新路**。

target 侧有 `_needs_seq_lens_cpu_sync` / `correct_optimistic_seq_lens_cpu()`
（`model_runner_v1.py:452-458`、`spec_decode/utils.py:41`）在 async spec decode 下把
`optimistic_seq_lens_cpu` 修正回来，`AscendAttentionBackend` 在该开关覆盖范围内，
所以大概率是安全的。但这条路径本次**没有实测**，回滚后如果接受率没有完全回到基线，
这里是第二个要看的点。

### [P3] 代码卫生

`attention_v1.py:335` 留了注释掉的旧行，`attention_v1.py:337` 有行尾空格。

### 第二步：如果确实要去掉这次 D2H

那次 `.tolist()` 是**语义上必需**的，不能简单换成 CPU 镜像——`num_rejected` 只在 device 上。
三个方向，按推荐度排序：

1. **把同步提前、改成异步。** 在 `set_inputs_first_pass()` 里算出 `cad.seq_lens`
   之后，立刻发起一次到 pinned host buffer 的 `non_blocking=True` 拷贝，builder 里再读。
   这样同步点从"launch 前阻塞"变成"和后续 host 侧准备工作重叠"，语义完全不变，改动最小。
2. **让 FIA 直接吃 tensor。** `attention_v1.py:354-356` 的注释已经说明
   `full_graph_fia_v2` 是把 seq_lens tensor 当 `actual_seq_kvlen` 传的；把
   parallel-drafting 的 draft 路径统一成传 tensor，就彻底不需要 host 值。改动面较大。
3. **同步维护 CPU 镜像。** 在 `set_inputs_first_pass()` 里同时给
   `cad.seq_lens_cpu` / `cad._seq_lens_cpu` 加 `+ N`。
   注意这**只能修掉 `+N` 那一半**，`- num_rejected` 在 async 路径下仍然拿不到，
   会变成 KV 窗口偏长 r 个 token（读到过期 KV）。**不推荐**，只是比现在偏短要好一点。

参考实现是 `llm_base_proposer.py:1755-1785`：那里 `extend_all_queries_by_N` 之后，
代码显式地把 `_seq_lens_cpu` 和 `seq_lens_cpu` 都做了 `+N`，并写了长注释说明
"NPU attention backends read those CPU mirrors as kernel input, so they MUST be in sync
with the GPU view"。dspark / dflash 的 `set_inputs_first_pass()` 没有遵守这个约定。

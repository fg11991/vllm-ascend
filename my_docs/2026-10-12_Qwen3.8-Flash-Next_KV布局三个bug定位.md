# Qwen3.8-Flash-Next 在 vLLM-Ascend PR #16981 上的 KV 布局三个 bug 定位

> 结论先行：**PR #16981 带 MTP 时在真机上起不来**，三个连续的启动失败全部源于 PR #17144 引入的 six-region KV cache 布局与 vLLM 自身 `block_size` 推导之间的口径不一致。不开 MTP + `--block-size 768` 可完全绕过，服务正常启动、真权重精度正常。
>
> 环境：Atlas 800 A3（64GB × 8，640 核）· 镜像 `quay.io/ascend/vllm-ascend:nightly-main-a3-openeuler`（2026-10-10，内含 vLLM v0.30.0）· vllm-ascend `6f56a5937` = main `ea01a44ba` + PR #16981 `c6d9e38f8` · 权重 `Qwen3.8-Flash-Next-w8a8-mtp`（W8A8，个人 msmodelslim 分支导出）
>
> 日期：2026-10-12

---

## 0 共同根源

三个 bug 全部来自 [vllm-project/vllm-ascend#17144](https://github.com/vllm-project/vllm-ascend/pull/17144)（"Re-group shattered GDN layers to cut Qwen3.8 KV cache groups from 39 to 6"）引入的 six-region 布局。关键事实：

- `vllm_ascend/core/six_region_kv_cache_layout.py` 和 `patch_kv_cache_utils.py` 的 QSA 部分在 **main 上完全不存在**（main 的 `patch_kv_cache_utils.py` 里 QSA 相关 0 处匹配）
- **#17144 自己从未合入 main**，最后更新 2026-09-21，OPEN 状态
- PR #16981 把 #17144 的代码带了进来，于是继承了它的全部口径问题
- 官方部署文档（`docs/source/tutorials/models/Qwen3.8-Flash-Next.md` 第 9 行）明确基于 **vLLM-Ascend 0.26.0rc**，而 `releases/v0.26.0rc` 分支里 qwen4_exp 文件数为 **0** —— 那份文档描述的是**另一套实现**，其启动命令对 #16981 不适用

因此「照抄官方文档命令」必然失败，这不是配置问题。

## 1 bug #1：`block_size=400` 违反 128 对齐

### 现象

```
ValueError: QSA block_size=400 violates kernel/compression alignment (ratio=4)
```

位置：`vllm_ascend/patch/platform/patch_kv_cache_utils.py:769`（`_prepare_qsa_composite_groups`）

### 定位

校验条件是两个条件合用一条报错信息：

```python
if main_spec.block_size % 128 or main_spec.block_size % ratio:
    raise ValueError(f"QSA block_size={...} violates kernel/compression alignment (ratio={ratio})")
```

`400 % 4 == 0` 是**合法**的，实际违反的是 `400 % 128 == 16`。**报错信息只打印了 `ratio`，没提 128，具有误导性。**

400 的来源在 vLLM `vllm/platforms/interface.py:922`：

```python
kernel_block_alignment_size = max(
    min(s.base if isinstance(s, MultipleOf) else s
        for s in backend_cls.get_supported_kernel_block_sizes()),
    cache_config.block_size,
)
attn_block_size = kernel_block_alignment_size * cdiv(
    mamba_page_size, kernel_block_alignment_size * attn_page_size_1_token)
...
if cache_config.block_size < attn_block_size:
    cache_config.block_size = attn_block_size     # ← 400 在此写入
```

不显式设 `--block-size` 时，Ascend backend 的最小支持块是 16，于是 `400 = 16 × 25`。

### 要点

`if cache_config.block_size < attn_block_size` 只在**用户设的值小于**计算值时覆盖。所以显式设一个 128 的倍数即可：`kernel_block_alignment_size` 变成该值，`attn_block_size = 128k × cdiv(...)` 仍是 128 的倍数，`% 128 == 0` 恒成立。

> 一个被否证的假设：曾推测 `mamba_page_size` 随 `mamba_cache_mode` 变化（即开关 prefix caching 会改变 400）。**实测否证** —— 恢复 `--enable-prefix-caching --mamba-cache-mode align` 后仍是 400。`mamba_page_size` 由模型 GDN state 布局决定（`interface.py:871` 的 `get_mamba_specs_from_config`），与 cache mode 无关。

## 2 bug #2：算出 512，six-region 期望 768

### 现象

设 `--block-size 128` 后，vLLM 算出 512，然后：

```
ValueError: language_model.model.layers.3.self_attn.attn block_size=512
            was not aligned before KV-cache grouping; expected 768
```

位置：`vllm_ascend/core/six_region_kv_cache_layout.py:240`

### 定位

六区布局要求 QSA main 的一个 block（`block_size` 个 token 的 K）**正好等于** GDN SSM state 的大小，六个区域才能打包进同一块物理内存：

```python
max_ssm_bytes = max(_state_bytes(spec, 1) for spec in gdn_specs)
k_token_bytes = spec.num_kv_heads * spec.head_size * get_dtype_size(spec.dtype)
aligned_block_size = max_ssm_bytes // k_token_bytes        # = 768
target_block_size = max(spec.block_size, aligned_block_size)
if spec.block_size != target_block_size:
    raise ValueError(f"... was not aligned before KV-cache grouping; expected {target_block_size}")
```

两处计算依据不同，且互不感知：

| 位置 | 依据 | per-token 字节 |
|---|---|---|
| vLLM `interface.py:922` | `mamba_page_size / attn_page_size_1_token` | 含 **K+V** |
| PR `six_region:231` | `max_ssm_bytes / k_token_bytes` | 只含 **K** |

两者差约 2 倍（768 vs 384~400 的量级吻合）。报错信息说 "was not aligned **before** KV-cache grouping"，但**没有任何代码会在 grouping 之前做这个对齐** —— PR 选择抛异常而不是自己对齐。

### 修法

`--block-size 768`。768 不会被 vLLM 覆盖：从 400 反推 `mamba_page_size ∈ (384, 400] × attn_page_size_1_token`，设 768 后 `kernel_block_alignment_size = max(16, 768) = 768`，`cdiv(...) = 1`，`attn_block_size = 768`，`if 768 < 768` 为假。三个约束同时满足：`768 % 128 == 0`、`768 % 4 == 0`、`max(768, 768) == 768`。

768 由 GDN SSM state 与 QSA K 的尺寸决定，**与 MTP、prefix caching 均无关**，在任何配置下都是这个模型在六区布局下的唯一正确值。

## 3 bug #3：raw cache page 2048 vs 2240（真正的拦路虎）

### 现象

```
ValueError: language_model.model.layers.3.self_attn.indexer.raw_key_cache
            six-region page mismatch: view=2048, region=2240.
```

位置：`vllm_ascend/worker/model_runner_v1.py:5951`

### 实测数据

在 `six_region_kv_cache_layout.py` 插入 DIAG 打印（只加日志，不动计算），dump 全部 13 个 `qsa_raw` owner：

| owner | block_size | num_heads | num_states | tokens_per_state | **head_size** | head_size_v | real page |
|---|---|---|---|---|---|---|---|
| `layers.3/7/…/47`（12 个） | 8 | 1 | 8 | 1 | **128** | 0 | **2048** |
| **`mtp.layers.48`** | 8 | 1 | 8 | 1 | **140** | 0 | **2240** |

`qsa_compressed` 的 13 个 owner（含 MTP）全部 `head_size=128`、`real=49152`，**完全一致** —— 问题只在 raw。

差异**只在 `head_size`**：MTP 层的 raw key cache 是 140 维，12 个主模型层是 128 维。

### 定位

| 位置 | 怎么算 | 值 |
|---|---|---|
| `six_region:275` | `max(_real_page_size_bytes(spec) for spec in QSA_RAW)` — 取**全部 owner 的 max** | 2240（MTP 贡献） |
| `model_runner_v1:5945` | `block_size × num_kv_heads × head_size × dtype_size` — **单层**手算 | 2048（layer 3） |

而 `real_page_size_bytes` 是 `unpadded_page_size_bytes` 的别名（vLLM `kv_cache_interface.py:526`）：

```python
unpadded_page_size_bytes = num_heads * num_states * state_content_size_bytes
state_content_size_bytes = (head_size + head_size_v) * get_dtype_size(dtype)
```

两者用 `!=` 比较，只要任何一层的 `head_size` 与最大者不同就必然失败。

### `head_size=140` 是上游设计，不是 PR 算错

上游 `vllm/models/qwen4_exp/common/qsa_cache.py:853`：

```python
return CircularBufferSpec(
    block_size=capacity, num_kv_heads=1,
    head_size=self.head_size,      # ← 每个 cache 实例自己的 head_size
    head_size_v=0, dtype=self.dtype,
)
```

`self.head_size` 由 `QSARawKeyCache` 实例持有。同一个 MTP 层的 `QSACompressedKeyCache` 仍是 128，说明 raw 与 compressed 是两个独立的 cache 类，维度本就可以不同。**head_size 不能改，改了影响数值。**

### 这个 `!=` 校验不能放宽

曾考虑把 `!=` 改成 `>`（允许 view 小于 region），**这会导致静默的数值错误**。`make_contiguous_slab_view`（`six_region_kv_cache_layout.py:349-367`）创建的是**连续** view，没有 per-block stride 参数：

```python
required_bytes = num_blocks * math.prod(item_shape) * dtype_size
result = backing[storage_offset : storage_offset + required_bytes].view(dtype).view(num_blocks, *item_shape)
assert result.is_contiguous()
```

它假定 block `i` 的数据位于 `storage_offset + i × prod(item_shape) × dtype_size`。若 region 按 2240/block 分配而 view 按 2048/block 连续读，**每个 block 都会错位 192 字节**。所以这个校验是在保护一个真实约束。

### 结论

**six-region 布局的「同角色 owner 共享一个 page size」假设，对带 MTP 的 Qwen4Exp 从来不成立。** 也就是说 #16981 + MTP 在真机上应该从未跑通过 —— 这与 PR 描述中 "Real A3 W8A8 TP8/DP1 single-request runs with MTP=3 and decode ACL Graph produced normal output" 的说法矛盾，除非那次验证用的是 six-region 合入之前的树。

## 4 绕过方案：不开 MTP

**抓 hidden 不需要 MTP** —— 第 3 步走 `/v1/completions` + `prompt=[token ids]` + `max_tokens=1`，纯 prefill，不做投机解码。不开 MTP 从根上消除 bug #3：

1. **那个 owner 消失了**：13 个 raw owner 变 12 个，全是 `head_size=128` → real page 全是 2048 → `max() == view`
2. **ring capacity 也变小**：上游 `qsa_cache.py:848`
   ```python
   span = self.compress_ratio + vllm_config.num_speculative_tokens
   capacity = self.compress_ratio * cdiv(span, self.compress_ratio)
   ```
   - MTP k=3：`span = 4+3 = 7` → `capacity = 8`（与 DIAG 实测的 `block_size=8` 吻合）
   - 无 MTP：`span = 4` → `capacity = 4`，raw page = `4 × 1 × 128 × 2 = 1024`，12 层一致
   且 `768 % 4 == 0`，上游 `block_size % capacity` 的断言也过

**无 MTP 时必须 `--enforce-eager`**：PR 描述明确说无 MTP 的 ACL Graph 路径会崩，需要上游 [vllm-project/vllm#58040](https://github.com/vllm-project/vllm/pull/58040)，而该修复**未包含在 #16981 中**。

### 实测结果（2026-10-12）

| 项 | 结果 |
|---|---|
| 服务启动（真权重，无 MTP，`--block-size 768`，eager） | ✅ 正常 |
| 精度 | ✅ 正常 |
| decode 吞吐 | ⚠️ **约 2 token/s**（eager + 无 MTP 的预期值；对 prefill-only 的 hidden 抓取无影响） |

## 5 如果要带 MTP（未验证的候选修法）

同角色 owner 的 page size 不一致时，让 `build_six_region_kv_cache_layout` 返回 `None`，回退到通用分配器。回退路径是**现成的设计**，不是硬造：

- `patch_kv_cache_utils.py:658` — 返回 `None` 时落到 `_orig_pool_bytes_per_block()`
- `model_runner_v1.py:5363` — 有 `uses_six_region_layout` 布尔开关与完整 else 分支
- `six_region_kv_cache_layout.py` 本身已有两处 `return None`（line 114、187）

候选补丁（插在 `main_pages = [` 之前）：

```python
for _role in (QSA_RAW, QSA_COMPRESSED, QSA_MAIN):
    _pages = {_real_page_size_bytes(_spec) for _, _spec in role_members[_role]}
    if len(_pages) > 1:
        logger.warning(
            "Six-region KV-cache layout disabled: role %s owners disagree "
            "on real page size (%s). Falling back to the generic allocator.",
            _role, sorted(_pages))
        return None
```

**未验证的风险**：回退路径能否处理 `CircularBufferSpec` 未知（上游有 `_try_get_full_allocation_fallback_groups`，见 `kv_cache_utils.py:2313`，但无人在此模型上验证）。若回退也失败，说明 six-region 对此模型是必需的，真正的修法只能是让 `make_contiguous_slab_view` 支持 per-block stride —— 结构性改动。另外放弃 six-region 会丢掉 #17144 的内存收益，可能 OOM。

## 6 给上游的反馈要点

1. **bug #1 的报错信息误导**：`patch_kv_cache_utils.py:769` 只打印 `ratio`，但 400 违反的是 128 对齐。建议把两个条件拆开或在信息里写明期望值
2. **bug #2 应主动对齐**：`six_region:240` 要求调用方在 grouping 前把 `block_size` 对齐到 `max_ssm_bytes // k_token_bytes`，但没有代码做这件事。建议 PR 自己对齐，或至少把期望值写进报错提示（目前确实写了 `expected 768`，这点是好的）
3. **bug #3 是设计缺陷**：six-region 的单 page size 假设与「同角色 owner 可有不同 head_size」的上游事实冲突。MTP 必然触发。建议按第 5 节回退，或支持 per-owner page size
4. **文档与实现错配**：官方部署文档基于 0.26.0rc（无 six-region），其命令对 #16981 不适用。另外文档里 `--speculative-config` 的 `"method":"qwen3_5_mtp"` 对本模型是**错的** —— `vllm/config/speculative.py:832` 把 `model_type` 从 `qwen4_exp` 映射为 `qwen4_exp_mtp`，而 `vllm_ascend/spec_decode/__init__.py:56` 认的正是 `qwen4_exp_mtp`。PR #15162 与 #17249 的文档都写对了，只有合入 main 的那份是错的

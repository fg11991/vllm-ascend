# Qwen3.8-Flash-Next hidden 抓取适配与 debug 全记录

## 摘要

> 为给 DSpark 草稿模型提供离线训练特征，需要让 vLLM-Ascend 侧的 Qwen4Exp 输出 auxiliary hidden states。上游只实现了 MTP，**完全没有** aux hidden 接口（`SupportsEagle3`/`aux_hidden_state` 在 `vllm/models/qwen4_exp/` 下 grep 为空）。本文记录该接口的实现、与 SpecForge 训练侧的逐项对齐结论，以及为把服务拉到可抓取状态所修的 5 个 bug。
>
> **最重要的单项成果是发现一个会导致静默掉点的索引陷阱**：Transformers 在 `attn_hyper_connection(...)` 返回值的 `[0]` 给出单流门控读出，而 vLLM 的 `GatedResidual.mix()` 在 `[0]` 给出的是 4 路残差原样透传、`[1]` 才是读出。照抄训练侧的 `output[0]` 会落盘 4×2560 的原始残差，而训练读取端对 4 维 hidden **静默按流求平均**而非报错 —— 与 DeepSeek-V4 锚点偏移同一类失败模式。
>
> 当前状态：aux hidden 接口与 34 个单测已完成并提交（`qwen38-capture` 分支），上游白名单与若干配置约束已解决，但**链路尚未端到端跑通** —— 仍阻塞在一个未定位的 `QSAStateBackend` 问题（第 5 节）。尚无落盘数据，因此 1.3 节的三项验收均未执行。

## 1. 背景与对齐契约

### 1.1 训练侧是标准答案

草稿模型由 SpecForge（`fg11991/specforge` 分支 `1008_next_flash`）训练，**训练侧实现即口径定义**，serving 侧每一处计算必须与之同义。

特征定义在 `specforge/offline_capture/qwen4_exp.py` 的 `hyper_connection_taps`：

```python
def record(_module, _args, output, *, key=layer_id):
    sink[key] = output[0]
handles.append(reader.attn_hyper_connection.register_forward_hook(record))
```

其 docstring 明确语义：`layers[i+1].attn_hyper_connection(streams)[0]` 是 **"the normalized input layer i+1's attention actually sees"**。

### 1.2 编号约定

两侧编号差 1，且方向容易搞反：

| | 语义 | 本模型取值 |
|---|---|---|
| SpecForge `target_layer_ids` | 第 i 层的**输出** | `[3, 15, 23, 35, 43]` |
| vLLM aux id | 第 k 层的**输入**（id 0 是 embedding） | `[4, 16, 24, 36, 44]` |

二者是同一个状态，`k = i + 1`。aux id 48（`= num_hidden_layers`）指最后一层之后，即 `hyper_connection_mixer` 的输出。

**加 1 发生在哪里（已核实）**：`vllm_ascend/worker/model_runner_v1.py:883-898` 覆写了 `_get_eagle3_aux_layers_from_config`，但它**先调 `super()`**（上游读 `eagle_aux_hidden_state_layer_ids`，**原样返回不加 1**），仅当上游返回空且 `use_dspark()` 为真时，才对 `dspark_target_layer_ids` / `target_layer_ids` 加 1。

因此：

- 阶段一（`extract_hidden_states`，非 dspark）：手写 `eagle_aux_hidden_state_layer_ids=[4,16,24,36,44,48]`，**不会被加两次**
- 阶段二（dspark）：草稿 config 保持 `target_layer_ids=[3,15,23,35,43]`，由 runner 加 1

`scripts/launch_vllm.py:66` 的 `include_last_layer` 追加的是 `num_hidden_layers`（48，不是 47），独立印证了 id 48 的语义。

### 1.3 逐项对齐结论

| # | SpecForge（标准答案） | vLLM-Ascend 侧 | 一致 |
|---|---|---|---|
| 1 | `layers[i+1].attn_hyper_connection(streams)[0]`，单流 2560 | `attn_hc.mix(...)[1]` = `block_input` | ✅ 同义 |
| 2 | hc_norm → 低秩 mix → 按 4 路加权求平均 | `grouped_gemma_rmsnorm(…, hc_norm.weight, …, hc_count)` → `input_mix_weight_down` → `hc_silu` → `input_mix_weight_up` → `hc_gate_mix(xn, gate, hc_count)` | ✅ 逐步对应 |
| 3 | `last_hidden_state` = `hyper_connection_mixer` 输出，无 final norm | `sample_hidden_states` = `Qwen4ExpModel.forward` 的返回值 | ✅ |
| 4 | tap 拒绝「下一层带 PLE」与「最后一层」 | reader 层 4/16/24/36/44 均不带 PLE（PLE 在第 1 层），均非末层 | ✅ |
| 5 | 5 个 tap 按 `target_layer_ids` **升序**拼成 12800 维 | `EagleModelMixin._set_aux_hidden_state_layers` 做 `tuple(sorted(set(layers)))` | ✅ 升序 |

## 2. 索引陷阱（本文最重要的发现）

### 2.1 现象

两个框架在同一语义位置的 tuple 索引**是反的**：

| | HF / SpecForge | vLLM `GatedResidual.mix()` |
|---|---|---|
| 门控读出（单流 2560，**要抓这个**） | `[0]` | **`[1]`** = `block_input` |
| 4 路残差 10240（**绝不能抓**） | 不在返回值里 | **`[0]`** = `hidden_states` 原样透传 |

### 2.2 证据

**训练侧**（`tests/test_offline_capture/test_hf_qwen4_exp.py:198-203`，断言写死）：

```python
streams = out.hidden_states[layer_id + 1]
self.assertEqual(streams.shape[-1], 4 * 64)        # 输入是 4 × hidden_size
expected = text.layers[layer_id + 1].attn_hyper_connection(streams)[0]
self.assertEqual(sink[layer_id].shape, (1, 30, 64))  # 输出 [0] 是单流 hidden_size
```

**serving 侧**（`vllm/models/qwen4_exp/amd/hyperconnection.py:127-150`）：

```python
xn = grouped_gemma_rmsnorm(hidden_states, self.hc_norm.weight, eps, self.hc_count)
lora = self.input_mix_weight_down(xn); lora = hc_silu(lora, self.hc_count)
gate = self.input_mix_weight_up(lora)
block_input = hc_gate_mix(xn, gate, self.hc_count)
return hidden_states, block_input, injection
#      ^^^^^^^^^^^^^  ^^^^^^^^^^^
#      [0] 4 流透传    [1] 单流读出
```

### 2.3 为什么后果是静默的

若误取 `mix()[0]`，落盘的是 `hc_count × hidden_size = 10240` 维原始残差。训练读取端（`specforge/algorithms/common/dflash_family_data.py` 的 `_normalize_hidden_states`）遇到 4 维 hidden **会按流求平均**（那是 DSV4 的口径）而非拒绝 —— 训练照常进行，接受率被悄悄吃掉。这与 DeepSeek-V4 那次「锚点差一位导致静默掉点」属同一类失败模式。

### 2.4 处置

三重防护，确保将来改回去会立刻失败：

1. 索引写成命名常量 `_BLOCK_INPUT_INDEX = 1`，模块 docstring 解释为何不是 0
2. 每次抓取校验宽度 `readout.shape[-1] == hidden_size`，不等则抛 `RuntimeError`（这同时覆盖 TP 分片的情况）
3. 单测 `test_readout_is_the_single_stream_not_the_residual` 直接断言捕获宽度是 `hidden_size` 而非 `hc_count * hidden_size`

## 3. aux hidden 接口实现

### 3.1 要抓的两处张量

| aux id | 对象 | 实现成本 |
|---|---|---|
| **48** | `sample_hidden_states` = `Qwen4ExpModel.forward` 的返回值（本模型无 final norm，故它直接就是 lm_head 输入） | **零改动**，`super().forward()` 拿到即是 |
| **4,16,24,36,44** | `block_input`，层 forward 的**局部变量**，不在返回值里 | 需旁路捕获 |

上游层 forward（`amd/model.py:305-318`）：

```python
hidden_states, block_input, injection = attn_hc.combine_and_mix(...)  # 或 attn_hc.mix(...)
...
attn_out = self.linear_attn(hidden_states=block_input)   # linear_attention 层
attn_out = self.self_attn(hidden_states=block_input, ...) # full_attention 层
```

注意我们的 5 个 id（4/16/24/36/44，均 ≡ 0 mod 4）全部落在 **GDN（linear_attention）** 层 —— QSA 在 ≡ 3 mod 4 的层。

### 3.2 捕获方式选择

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 重写 `Qwen4ExpDecoderLayer.forward` | 复制上游约 50 行，上游一改就要同步 |
| **B（采用）** | per-instance 包装目标层 `attn_hyper_connection` 的 `mix` / `combine_and_mix` | 改动最小，不复制上游逻辑，**纯读取不改计算**；`attn_hyper_connection` 是每层独立的 `GatedResidual` 实例，只包装 5 层，`mlp_hyper_connection` 与其他层完全不碰 |
| C | forward hook | 不可行，hook 拿不到局部变量 |

一个需避开的坑：`EagleModelMixin._maybe_add_hidden_state()`（`interfaces.py:1601`）的默认语义是 `hidden_states + residual`，那是标准 pre-norm transformer 的残差相加，**不能用** —— 口径要求不对 4 路做任何相加或平均。

### 3.3 自检（`VLLM_ASCEND_QWEN4EXP_AUX_HIDDEN_SELF_CHECK`，默认 0）

- **aux id k**：额外包装该层 attention 的 `forward`，断言 `consumed is captured` —— 用**对象同一性**而非数值相等，比「差为 0」更强，能捕获任何中间替换
- **id 48**：断言返回列表里 mixer 那一槽 `is final_hidden_states`

| 级别 | 问题 | 根因 | 处置 |
|---|---|---|---|
| P1 | forward 签名改成 `*args, **kwargs` 后动态维度标记全失效 | 上游 `_mark_dynamic_inputs` **按参数名**定位 `input_ids`、`positions` 等张量 | 恢复与上游逐项一致的显式签名；加 `inspect.signature` 对比测试与 VAR_POSITIONAL/VAR_KEYWORD 禁用测试 |

## 4. 修掉的 5 个 bug

### 4.0 总览

| # | 现象 | 根因 | 处置 | 状态 |
|---|---|---|---|---|
| 1 | `block_size=400 violates kernel/compression alignment (ratio=4)` | 实际违反 128 对齐；报错只打印 `ratio` 具误导性 | `--block-size 768` | ✅ |
| 2 | `block_size=512 was not aligned before KV-cache grouping; expected 768` | vLLM 按 K+V/token 推导，PR 按仅 K 推导，差约 2 倍 | 同上 | ✅ |
| 3 | `raw_key_cache six-region page mismatch: view=2048, region=2240` | MTP 层 raw cache `head_size=140` ≠ 主模型 128；layout 取 owner max、runner 算单层 | 不开 MTP（抓取不需要） | ✅ 绕过 |
| 4 | `Qwen4Exp speculative decoding supports only its native MTP checkpoint and linear n-gram proposers` | 上游白名单 `{mtp, ngram, ngram_gpu}` 不含 `extract_hidden_states` | patch：调用上游时临时摘掉 `speculative_config` | ✅ |
| 5 | 显存：4608 token 需 20.6 GiB，预算仅 11.83 GiB | `CircularBufferSpec` 的 ring 容量污染 token-indexed gcd，hidden cache block_size 塌到 8，block 数被放大 96 倍 | 实现修正但**默认关闭**；改用更短的 `max-model-len` | ⚠️ 规避 |

全部 5 个都源自 PR #16981 继承自 **PR #17144（six-region KV 布局，OPEN 未合入）** 的代码，或与之交互。核查确认 `six_region_kv_cache_layout.py` 与 `patch_kv_cache_utils.py` 的 QSA 部分在 **main 上完全不存在**（后者 QSA 相关匹配 0 处）。

### 4.1 bug #1：报错信息掩盖了真实约束

校验条件把两个条件合用一条报错信息（`patch_kv_cache_utils.py:769`）：

```python
if main_spec.block_size % 128 or main_spec.block_size % ratio:
    raise ValueError(f"QSA block_size={...} violates kernel/compression alignment (ratio={ratio})")
```

`400 % 4 == 0` 是**合法**的，实际违反的是 `400 % 128 == 16`。400 的来源是 `vllm/platforms/interface.py:922`，Ascend backend 最小支持块为 16，故 `400 = 16 × 25`。

**一个被实测否证的假设**：曾推断 `mamba_page_size` 随 `mamba_cache_mode` 变化（即开关 prefix caching 会改变 400）。恢复 `--enable-prefix-caching --mamba-cache-mode align` 后仍是 400 —— `mamba_page_size` 由模型 GDN state 布局决定（`interface.py:871`），与 cache mode 无关。该弯路花了一轮。

### 4.2 bug #2：两处推导依据不同

六区布局要求 QSA main 的一个 block（`block_size` 个 token 的 K）**正好等于** GDN SSM state 大小，六个区域才能打包进同一块物理内存（`six_region_kv_cache_layout.py:223-240`）：

| 位置 | 依据 | per-token 字节 |
|---|---|---|
| vLLM `interface.py:922` | `mamba_page_size / attn_page_size_1_token` | 含 **K+V** |
| PR `six_region:231` | `max_ssm_bytes / k_token_bytes` | 只含 **K** |

两者差约 2 倍（768 vs 384~400 的量级吻合）。报错说 "was not aligned **before** KV-cache grouping"，但**没有任何代码会在 grouping 前做这个对齐** —— PR 选择抛异常而非自行对齐。

设 `--block-size 768` 后不会被 vLLM 覆盖：从 400 反推 `mamba_page_size ∈ (384, 400] × attn_page_size_1_token`，设 768 后 `kernel_block_alignment_size = max(16, 768) = 768`，`cdiv(...) = 1`，`attn_block_size = 768`，`if 768 < 768` 为假。768 同时满足三个约束：`% 128 == 0`、`% 4 == 0`、`== max_ssm_bytes / k_token_bytes`。

### 4.3 bug #3：MTP 层的 raw cache 宽度与主模型层不同（最关键）

**现象**：`model_runner_v1.py:5951` 报 `view=2048, region=2240`。

**证据**：在 `six_region_kv_cache_layout.py` 插入 DIAG 打印（只加日志不动计算），dump 全部 13 个 `qsa_raw` owner：

| owner | block_size | num_heads | num_states | tokens_per_state | **head_size** | head_size_v | real page |
|---|---|---|---|---|---|---|---|
| `layers.3/7/…/47`（12 个） | 8 | 1 | 8 | 1 | **128** | 0 | **2048** |
| **`mtp.layers.48`** | 8 | 1 | 8 | 1 | **140** | 0 | **2240** |

`qsa_compressed` 的 13 个 owner（含 MTP）全部 `head_size=128`、`real=49152`，**完全一致** —— 差异只在 raw，且只在 `head_size`。

**根因**：

| 位置 | 怎么算 | 值 |
|---|---|---|
| `six_region:275` | `max(_real_page_size_bytes(spec) for spec in QSA_RAW)` — 取**全部 owner 的 max** | 2240（MTP 贡献） |
| `model_runner_v1:5945` | `block_size × num_kv_heads × head_size × dtype_size` — **单层**手算 | 2048（layer 3） |

两者用 `!=` 比较，只要任何一层的 `head_size` 与最大者不同就必然失败。

**`head_size=140` 是上游设计，不是 PR 算错**：`vllm/models/qwen4_exp/common/qsa_cache.py:853` 中 `CircularBufferSpec(head_size=self.head_size, ...)`，`self.head_size` 由 `QSARawKeyCache` 实例持有；同一 MTP 层的 `QSACompressedKeyCache` 仍是 128，说明 raw 与 compressed 是两个独立 cache 类，维度本就可以不同。**head_size 不能改，改了影响数值。**

**这个 `!=` 校验也不能放宽**。曾考虑改成 `>`（允许 view 小于 region），**会导致静默数值错误**：`make_contiguous_slab_view`（`six_region_kv_cache_layout.py:349-367`）创建的是**连续** view，没有 per-block stride 参数，它假定 block `i` 位于 `storage_offset + i × prod(item_shape) × dtype_size`。若 region 按 2240/block 分配而 view 按 2048/block 连续读，**每个 block 错位 192 字节**。

**结论**：six-region 的「同角色 owner 共享一个 page size」假设，对带 MTP 的 Qwen4Exp **从来不成立**。这与 PR 描述中 "Real A3 W8A8 TP8/DP1 single-request runs with MTP=3 and decode ACL Graph produced normal output" 的说法矛盾，除非那次验证用的是 six-region 合入之前的树。

**处置：不开 MTP**，从根上消除：

1. 该 owner 消失：13 个 raw owner 变 12 个，全是 `head_size=128` → `max() == view`
2. ring capacity 也变小：`span = compress_ratio + num_speculative_tokens`，`capacity = compress_ratio × cdiv(span, compress_ratio)`（`qsa_cache.py:848`）
   - MTP k=3：`span = 7` → `capacity = 8`（与 DIAG 实测的 `block_size=8` 吻合）
   - 无 MTP：`span = 4` → `capacity = 4`

无 MTP 时必须 `--enforce-eager`：PR 描述声明无 MTP 的 ACL Graph 路径需上游 [vllm#58040](https://github.com/vllm-project/vllm/pull/58040)，该修复未包含在 #16981 中。

**候选修法（未验证）**：同角色 owner page size 不一致时让 `build_six_region_kv_cache_layout` 返回 `None`，回退通用分配器。回退路径是现成设计（`patch_kv_cache_utils.py:658` 落到 `_orig_pool_bytes_per_block`；`model_runner_v1.py:5363` 有 `uses_six_region_layout` 开关与完整 else 分支；该文件本身已有两处 `return None`）。风险：回退路径能否处理 `CircularBufferSpec` 未知，且放弃 six-region 会丢掉 #17144 的内存收益。**这是解除 MTP 阻塞的下一步。**

### 4.4 bug #4：extract_hidden_states 不在 speculative 白名单

上游 `vllm/model_executor/models/config.py:890` 的白名单写成函数体内的字面量集合：

```python
if spec_config is not None and spec_config.method not in {"mtp", "ngram", "ngram_gpu"}:
    raise NotImplementedError("Qwen4Exp speculative decoding supports only its native MTP checkpoint and linear n-gram proposers")
```

**该拒绝理由对 capture 不适用**：`extract_hidden_states` 不是 proposer，它不加载草稿模型、不预测任何 token，只把 aux hidden 路由进一个 cache-only 层供 KV connector 写出。Ascend 侧该有的配套都在（`spec_decode/extract_hidden_states_proposer.py`，以及 `patch_mamba_config.py:155-161` 对同一 connector 的 mamba cache mode 豁免）。

白名单是字面量无法就地扩展，故 patch 的做法是：**只在调用上游时摘掉 `speculative_config`，之后 `finally` 恢复**。两条依据支撑其安全性：

1. 父类 `Qwen3_5ForConditionalGenerationConfig` 从不读 `speculative_config`（grep 计数 0）
2. Qwen4Exp 自己的函数体内，`speculative_config` **只**出现在那个白名单检查里

因此 hc_count、PLE/QSA vs DBO/microbatching、PLE vs PP>1、M-RoPE stripping 等校验全部照旧生效。8 个测试覆盖：豁免生效、mtp/ngram/ngram_gpu/dspark 原样放行、无 spec config 的情况、上游抛别的错时配置仍被恢复、patch 确实装在上游类上。

只需 patch `Qwen4ExpForConditionalGenerationConfig` 一个类：`Qwen4ExpForCausalLMConfig` 与 `Qwen4ExpMTPConfig` 虽各自覆写该方法，但都显式调用父类的，那次属性查找会解析到装上去的函数；再 patch 它们会双重包装。

### 4.5 bug #5：显存 —— 一次改错与一条真正的放大链

这是本次耗时最多、也最值得记录的一项，因为**第一次修错了**。

#### 第一次尝试（已撤销）

`vllm_ascend/worker/worker.py:703` 原有一个豁免，专为 Qwen4Exp 这种打包布局保留全额预算，其条件含 `kv_transfer_config is None`。capture 模式必须设 connector，于是被排除，预算被按 group 缩放 **0.4865** → 仅 11.83 GiB。

当时据注释「compressed QSA descriptor 是同一块 page-strided backing 的逻辑视图」判断该排除对我们不成立，遂放宽。结果预算涨到 24.98 GiB，但**分配阶段 OOM**，且降 `gpu-memory-utilization` 反而更差（0.93 时差 69 MiB，0.90 时差 228 MiB）。

**为什么错**：`vllm/v1/core/kv_cache_utils.py:2296-2307` 先把 `HiddenStateCacheSpec` 从 packed spec 中剔除，再作为**独立 group** append。capture 模式确实携带一份 packed 分配之外的 page，「所有 group 共享一块 packed backing」的前提不成立。`utilization` 调不动是因为超额是结构性的，不是余量不足。

**教训**：当时只读了那个豁免的注释就采信其前提，没去核查 hidden cache 是否真在 packed backing 里。

#### 真正的放大链

| 环节 | 值 | 来源 |
|---|---|---|
| `num_speculative_tokens` | **1**（硬性） | `extract_hidden_states.py:35` 的 `assert self.num_speculative_tokens == 1` |
| QSA ring capacity | `4 × cdiv(4+1, 4)` = **8** | `qsa_cache.py:848` |
| `group_block_size` = gcd(768, **8**, 4608) | **8** | `kv_cache_utils.py:2325` |
| hidden cache block_size | `_largest_divisor_at_most(8, 25)` = **8** | 同上第 2329 行 |
| block 数（4608 token） | **576** | 由最小 block_size 决定 |
| 每 block 代价 | **36.6 MiB**（six-region 占 35.85，hidden cache 仅 0.75） | — |
| 总需求 | **20.2 GiB**（engine 实报 20.6） | — |

实测两点验证了线性关系：`8192 → 37.47 GiB`、`6144 → 28.14 GiB`，均为 **4.576 MiB/token**。

**浪费的本质**：six-region 实际只需 `4608/768 = 6` 个 block，却被分配 576 个 —— **96 倍**，因为所有 group 共享同一 block 索引空间，而 hidden cache 的 `block_size=8` 把 block 数定死了。同时 `8 × 30720 = 245760` 只填满 `786432` 字节 page 的 31%，浪费 68.75%。

**`CircularBufferSpec` 不该参与这个 gcd**：它的 `block_size` 是环中存几行 key，而 `max_num_blocks_per_req()` 返回 **1**（`kv_cache_interface.py:884`，注释 "The ring occupies one block per request for its whole lifetime"）—— 它从不按 token 索引 block。排除后 `gcd(768, 4608) = 768`：

| | 现在 | 排除 ring 后 |
|---|---|---|
| hidden block_size | 8 | **24** |
| block 数（4608 token） | 576 | **192** |
| 每 token 成本 | 4.576 MiB | **1.525 MiB** |
| page 浪费 | 68.75% | **6.25%** |
| 4608 token 需要 | 20.6 GiB | **6.7 GiB** |

#### 处置：实现但默认关闭

该修正**未在真机验证**，且风险是静默的：无法证明不同 block_size 的 group 可安全共存于同一 block-id 空间（block manager 路径未逐行走完），推断错误会导致 `slot_mapping` 偏移、抓到错数据而不报错。

归因分级：
- **强证据**：`CircularBufferSpec` 自己声明 one-block-per-request；gcd 的用途是让 hidden cache 与 token-indexed group 对齐；96 倍超分配不像有意设计
- **未证明**：不同 block_size 混用的安全性

因此实现保留在 `VLLM_ASCEND_QWEN4EXP_WIDEN_HIDDEN_CACHE_BLOCKS` 后面（**默认 0**），env 变量注释写明启用前必须通过的验证。

**当前采用的替代方案**：用更短的 `max-model-len`。验证训练有效性只需约 200 条样本，序列长度并非硬要求 —— 上游原始行为在缩放预算下可服务约 2544 token（engine 自报），`--max-model-len 2304`（= 768×3）即可满足，**零代码改动、零静默风险**。

**启用前必须做的验证**（设计好但未执行）：在两者都能服务的 `max-model-len`（如 2304）下，分别以开关关闭/开启各抓同一条样本，逐位对比 `token_ids` 与 `hidden_states`。全部 `identical` 才说明推断成立。

## 6. 落盘格式与启动配置（已确认，待实测）

格式来自 `vllm/distributed/kv_transfer/kv_connector/v1/example_hidden_states_connector.py`：

| 项 | 值 |
|---|---|
| 文件 | `{shared_storage_path}/{req_id}.safetensors` + 伴随 `{...}.safetensors.lock` |
| 张量 | `hidden_states`、`token_ids` |
| 路径回传 | 响应的 `kv_transfer_params["hidden_states_path"]` |
| 读取 | `load_hidden_states(path)`，用 `flock(LOCK_SH)` 阻塞等写完（不轮询） |
| 提取 | `extract_from_kv_cache`：`kv_cache[slot//bs, :, slot%bs][:num_tokens]` |
| 第二维顺序 | 6 个 id 按**升序**（`_set_aux_hidden_state_layers` 做 `sorted`），与 SpecForge 升序拼接一致 |

启动配置取自 speculators `scripts/launch_vllm.py:81-110`，`draft_model_config.hf_config` 是**内联**的，无需真实 draft 目录：

```python
speculative_config = {"method": "extract_hidden_states", "num_speculative_tokens": 1,
                      "draft_model_config": {"hf_config": {"eagle_aux_hidden_state_layer_ids": [4,16,24,36,44,48]}}}
kv_transfer_config = {"kv_connector": "ExampleHiddenStatesConnector", "kv_role": "kv_producer",
                      "kv_connector_extra_config": {"shared_storage_path": "..."}}
```

**chunked prefill 与 prefix caching 必须关闭**：

- prefix caching **必然**破坏抓取：命中缓存的 token 不会重新 forward，其 aux hidden 根本不会生成，落盘的 `token_ids` 与 `hidden_states` 的 T 对不上
- chunked prefill 关闭是**保守选择**而非已证明有问题：speculators 无条件追加 `--no-enable-chunked-prefill`；GDN 递归 state 与 PLE n-gram 在 chunk 边界的行为未逐行验证；而 200 条短样本不需要它
- 注意 `enable_prefix_caching` 在 vLLM 中**默认为 `True`**（`config/cache.py:130`），必须显式 `--no-enable-prefix-caching`，否则 `mamba_cache_mode` 被自动设为 `align`，与 `--no-enable-chunked-prefill` 冲突（`models/config.py:641` 的 assert）
- 这与 `patch_mamba_config.py:155-161` 的预设一致：extract_hidden_states 场景应「Leave the mode as vLLM derived it (e.g. "none" when prefix caching is off)」

|---|---|---|
| 2300 token | ≈ 69 MB | **≈ 14 GB** |
| 3000 token | ≈ 90 MB | ≈ 18 GB |

磁盘不构成约束。纯 prefill 抓取，即使 prefill 仅 1000 token/s，200 条也是分钟级。

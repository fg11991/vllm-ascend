- **vllm-ascend main 完全没有 qwen4_exp 实现**：只有一份部署文档（PR #17024），`envs.py` 里 QSA 变量 0 个，`hardware_profile.py` 里 QSA capability 0 个。必须叠 PR #16981。

- **版本配对天然成立**：#16981 复用上游 `vllm.models.qwen4_exp.amd`（不 vendor 模型代码）。该模块 vLLM v0.28.0 **无**、v0.29.0 起**有**；而 vllm-ascend main 自 #16527（2026-09-23）起 pin `VLLM_TAG=v0.30.0`。PR 描述里"v0.28 不含该模块"的顾虑**已过时**。

## 1 环境确认（每次进容器先跑）

```bash
echo "=== 权重 ===" && ls -d /models/Qwen3.8-Flash-Next-w8a8-mtp && echo "=== capture 可写 ===" && (touch /capture/.t && echo yes && rm /capture/.t) && echo "=== 代码树 ===" && git -C /vllm-workspace/vllm-ascend log -1 --format='%h %s' && echo "=== 真实可用核数 ===" && env -u OMP_NUM_THREADS -u OMP_THREAD_LIMIT nproc && python3 -c 'import os; print("sched_getaffinity:", len(os.sched_getaffinity(0)))'
```

期望：权重可见、capture 可写、代码树是 `6f56a5937`、核数 640。

> **`nproc` 陷阱**：`nproc` 会读 `OMP_NUM_THREADS` / `OMP_THREAD_LIMIT` 并以其为上限。本机设了 `OMP_NUM_THREADS=1`，所以裸跑 `nproc` 返回 1，但这**不是** CPU 限制 —— `os.sched_getaffinity(0)` 是 640。cgroup 和亲和性从未受限。编译时必须 `env -u` 掉这两个变量，否则并行度被压成 1。

## 3 自定义算子编译（可选）

### 为什么可选

PR #16981 对 C++ 的改动**只有一处**：新算子 `qsa_expand_e3`。

- `csrc/torch_binding.cpp`：1 个 include + 1 个 `qsa_expand_e3_out` 注册
- `csrc/torch_binding_meta.cpp`：1 个 meta 函数 + 1 个注册

别无其他 C++ 改动。所以**镜像里预编好的 `vllm_ascend_C` 和 41 个算子已经够用**，只要放弃 E3。

`use_e3` 只控制最后一步 block→token 索引展开：

| `use_e3` | 走的实现 | 需要新算子 |
|---|---|---|
| `True` | `expand_qsa_block_indices_e3` | 是 |
| `False` | `expand_qsa_block_indices_npu` | 否 |

而 **Lightning Indexer 本体用 `torch.ops.npu.npu_lightning_indexer`（CANN 原生算子）**，不是 vllm-ascend 自编的，所以 E3 关掉后 Lightning 照常工作。

**结论：`VLLM_ASCEND_ENABLE_QSA_E3V=0` 时零编译即可运行，功能和数值不受影响，只损失 E3 的索引展开融合性能。第 2、3 步抓 hidden 完全不依赖它。**

### 零编译路径验证

```bash
cd /vllm-workspace/vllm-ascend && source /usr/local/Ascend/ascend-toolkit/set_env.sh && source /usr/local/Ascend/nnal/atb/set_env.sh && ls vllm_ascend/_cann_ops_custom/ && du -sh vllm_ascend/_cann_ops_custom/ && python -c "
import torch, vllm_ascend
from vllm_ascend.models.qwen4_exp import qsa, lightning_indexer
print('qwen4_exp wrappers OK')
print('npu_lightning_indexer:', hasattr(torch.ops.npu, 'npu_lightning_indexer'))
print('qsa_expand_e3_out:', hasattr(torch.ops._C_ascend, 'qsa_expand_e3_out'))
" 2>&1 | grep -v "^INFO\|^\[W\|Available plugins\|Platform plugin\|Breakable"
```

期望：`_cann_ops_custom/` 含 `vendors`（约 46M）、wrappers import OK、`npu_lightning_indexer: True`、`qsa_expand_e3_out: False`。

> `qsa_expand_e3_out: False` 是**正常的** —— 它返回 `False` 而非抛异常，说明 `_C_ascend` namespace 已加载，只缺这一个 op。
>
> 注意 `hardware_profile` 里 `QSA_E3_EXPAND` 会报 `True`，那是**硬件**能力，不代表算子已编译。所以必须显式设 `VLLM_ASCEND_ENABLE_QSA_E3V=0`，否则运行时会去找不存在的算子。

### 可选：完整编译（拿到 E3）

**已知风险**：PR 作者明确声明 rebase 后未重跑 NPU 端到端验证，而该 PR 落后当前 main 65 个 commit。`qsa_expand_e3` 能否编译通过是未知数。首次尝试失败过（`ninja: build stopped: subcommand failed`，但当时并行度被 `OMP_NUM_THREADS=1` 压成 1，真实报错未取到）。

A3 分支要编 42 个算子，第三方 protobuf 单线程耗时 1277 秒；多线程下预计十几分钟。


失败时提取报错：

```bash
grep -n -i -E "error:|fatal|FAILED:|undefined reference" /capture/aclnn_build.log | head -30
```

```bash
grep -n "qsa_expand_e3" /capture/aclnn_build.log | head -20 && echo "=== 首个失败上下文 ===" && awk '/FAILED:|error:/{f=NR} f && NR>=f-5 && NR<=f+25' /capture/aclnn_build.log | head -60
```

## 4 拉起服务（MTP k=3 基线）

```bash
cd /capture && unset CPLUS_INCLUDE_PATH CPATH C_INCLUDE_PATH && source /usr/local/Ascend/ascend-toolkit/set_env.sh && source /usr/local/Ascend/nnal/atb/set_env.sh && export VLLM_ASCEND_ENABLE_QSA_LIGHTNING_INDEXER=1 && export VLLM_ASCEND_ENABLE_QSA_E3V=0 && unset VLLM_ASCEND_FORCE_QSA_REFERENCE && export OMP_NUM_THREADS=32 && nohup vllm serve /models/Qwen3.8-Flash-Next-w8a8-mtp --host 0.0.0.0 --port 9811 --served-model-name qwen3.8-flash-next --trust-remote-code --quantization ascend --tensor-parallel-size 8 --data-parallel-size 1 --enable-expert-parallel --max-model-len 32768 --max-num-seqs 16 --max-num-batched-tokens 4096 --gpu-memory-utilization 0.93 --language-model-only --enable-auto-tool-choice --tool-call-parser qwen3_xml --reasoning-parser qwen3 --compilation-config '{"cudagraph_capture_sizes":[4,8,12,16,20,24,28,32],"cudagraph_mode":"FULL_DECODE_ONLY"}' --speculative-config '{"method":"qwen3_5_mtp","num_speculative_tokens":3,"enforce_eager":true}' --additional-config '{"enable_cpu_binding":true,"ascend_compilation_config":{"fuse_norm_quant":false}}' > /capture/serve_mtp3.log 2>&1 &
```

### 相对官方文档命令的改动与理由

官方已验证命令见 `docs/source/tutorials/models/Qwen3.8-Flash-Next.md` 第 5.1 节。本手册的改动：

| 改动 | 理由 |
|---|---|
| `--port 9811` | 官方示例用 8088，但本容器只映射了 9811/29813，8088 在宿主上访问不到 |
| `--max-model-len` 135168 → **32768** | 训练样本最长 4096，需求是 ≥8192。降下来给并发腾显存 |
| **去掉** `--enable-prefix-caching --mamba-cache-mode align` | 第 3 步抓 hidden 要求关闭 prefix caching；第 1 步就关以保持口径一致，同时避开文档标注的"实验性" |
| **加** `--language-model-only` | 只抓文本 hidden，不需要 vision encoder，省显存 |
| `--max-num-seqs` 8 → **16** | 为后续吞吐测试留空间；OOM 则退回 8 |
| `VLLM_ASCEND_ENABLE_QSA_E3V=0` | 零编译路径，见第 3 节 |
| `OMP_NUM_THREADS=32` | 本机默认 1 会拖慢权重加载；640 核上不限制又会导致线程争抢。32 是折中，**待实测调优** |

### 5.1 基础连通

```bash
curl -s http://127.0.0.1:9811/v1/chat/completions -H "Content-Type: application/json" -d '{"model":"qwen3.8-flash-next","messages":[{"role":"user","content":"用一句话解释什么是投机推理。"}],"max_tokens":128}' | python3 -m json.tool
```

### 5.2 训练数据渲染口径（思考模式）

**`reasoning_effort` 是 `/v1/chat/completions` 的顶层参数**，不放在 `chat_template_kwargs` 里。vLLM v0.30.0 `chat_completion/protocol.py:245` 的合法取值为 `none|minimal|low|medium|high|xhigh|max`，`xhigh` 合法。`build_chat_params()` 会把它注入 `chat_template_kwargs` 并自动补 `enable_thinking = (reasoning_effort != "none")`，所以 `enable_thinking` 不必手传。

```bash
curl -s http://127.0.0.1:9811/v1/chat/completions -H "Content-Type: application/json" -d '{"model":"qwen3.8-flash-next","messages":[{"role":"user","content":"9.11 和 9.9 哪个大？"}],"reasoning_effort":"xhigh","max_tokens":512}' | python3 -m json.tool
```

> **`preserve_thinking` 待确认**：它不是 vLLM 的参数，只可能是本权重 `chat_template.jinja` 自己的变量，须经 `chat_template_kwargs` 传入。而 `resolve_chat_template_kwargs` 会**静默丢弃**模板不认识的变量 —— 名字写错不报错，只是不生效，导致渲染口径与 SpecForge 的 loss mask 不一致。先取真实变量名：
>
> ```bash
> grep -o "preserve[a-z_]*\|reasoning_effort\|enable_thinking\|thinking[a-z_]*" /models/Qwen3.8-Flash-Next-w8a8-mtp/chat_template.jinja | sort -u
> ```

## 7 已知问题与规避

| 问题 | 规避 |
|---|---|
| `qsa_expand_e3` 未编译 | `VLLM_ASCEND_ENABLE_QSA_E3V=0`，走 `expand_qsa_block_indices_npu`，数值不变 |
| 无 MTP 时 ACL Graph 崩溃 | 需上游 vllm#58040，**未包含在 #16981 中**。第 3 步抓 hidden 若关 MTP，必须用 eager |
| PR #16981 未经 rebase 后 NPU 验证 | 作者明确声明；遇到问题先给最小复现再定位 |
| `nproc` 返回 1 | `OMP_NUM_THREADS` 作祟，见第 1 节 |
| Lightning Indexer 静默降级 | `_lightning_indexer_eligible` 硬条件：`query.shape[1] <= 64`、`head_dim == 128`、`compress_ratio == 4`、`token_topk == 2048`、cache shape `(192,1,128)`。不满足则**静默**退到 triton 选择器，性能下降但不报错。TP8 下需打点确认实际走的路径 |
| `/opt` 下有同事工作区 | 若挂载了 `/opt`，注意 `/opt/w00498770`、`/opt/t828158` 下的 `cpython-311` `.so` 与本容器 Python 3.12 不匹配，是旧环境残留，勿误用、勿写入 |

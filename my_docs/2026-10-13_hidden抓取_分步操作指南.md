## 第一步 验证链路（合成数据）

目的：在投入真实数据前，确认通路、落盘格式、确定性都正确。用脚本自己造的 token id，不需要你准备任何数据。

```bash
cd /vllm-workspace/vllm-ascend && python3 my_docs/scripts/verify_capture.py --lengths 100,500,2000 2>&1 | tee /opt/w00958190/log/verify_capture.log
```

### 它检查什么

| 检查 | 对应验收项 |
|---|---|
| 响应的 `prompt_token_ids` 与发出的 ids 逐位相同 | 「token_ids 与发出的完全一致」 |
| 落盘 `token_ids` 也逐位相同，且 **T == prompt 长度** | 同上 |
| `hidden_states` 形状 `[T, 6, 2560]`、dtype `bfloat16`、无 NaN/Inf | 落盘格式 |
| 同一条样本抓两次 **逐位相同** | 「同一条样本跑两次，结果确定」 |
| 实测 token/s、KB/token，外推 200 条耗时与磁盘 | 吞吐 |

请求形状严格按要求：`/v1/completions` + `prompt=[token ids]` + `max_tokens=1` + `return_token_ids=true`，**不经服务端渲染 chat template**（照 speculators 的 `vllm_client.generate_hidden_states` 抄的）。

### 预期输出

```
--- length 100 ---
  prompt_token_ids  : matches (100 ids)
  hidden_states_path: /opt/w00958190/capture/<req_id>.safetensors
  hidden_states     : shape (100, 6, 2560) dtype torch.bfloat16
  token_ids         : shape (100,) dtype torch.int64
  OK                : T=100 matches prompt length, 3.1 MB on disk, ...
...
--- determinism (same sample twice) ---
  hidden_states     : identical=True
  OK                : capture is deterministic for this sample
```

### 这一步可能的失败

| 现象 | 原因与处置 |
|---|---|
| `torch.cuda` 相关 AttributeError | `ExampleHiddenStatesConnector` 的写盘路径用 `torch.cuda.Event`/`Stream`。初始化阶段已验证通过，但 `_submit_async_write` 还没跑过。**把 traceback 给我**，需要写一个 NPU 版 connector |
| `hidden_states shape is (T, 1, 15360), expected (T, 6, 2560)` | 我按 `extract_hidden_states.py:356-362` 推断 `num_kv_heads=6`、`head_size=2560`。若实际不同，加 `--num-aux 1 --hidden-size 15360` 先跑通，再对齐 SpecForge 侧的 reshape |
| `expected the full hidden size 2560`（服务端崩） | TP8 下 hyper_connection 吐的是 per-rank 分片。这是我在 `aux_hidden.py` 里的**硬失败保护**，宁可崩也不静默落盘错数据。需要在抓取侧做 all-gather |
| `response has no kv_transfer_params` | connector 没配上，检查启动命令的 `--kv_transfer_config` |
| `identical=False` | 抓取不确定。**立即停下告诉我**，这会直接污染训练数据 |

## 第二步 抓真实数据集

### 2.1 你需要提供什么

一个 JSONL 文件，**每行一条样本，token id 已由 SpecForge 侧渲染好**：

```json
{"id": "sample-0001", "input_ids": [151644, 872, 198, ...]}
{"id": "sample-0002", "input_ids": [151644, 872, 198, ...]}
```

- `input_ids` 必需；`id` 可选（默认用行号），它决定落盘文件名
- 其他字段（如 `loss_mask`、来源标记）会**原样带进 manifest**，方便你那边的转换器对应
- **token id 必须由你那边生成**，用 SpecForge 的渲染（开思考、`reasoning_effort=xhigh`、保留历史 reasoning）。serving 侧不做任何渲染，这样 loss mask 和 token 才能一一对应

> **长度上限**：当前服务 `--max-model-len 2304`，所以样本最长 2304 token。更长的要么被 `--max-tokens-per-sample` 跳过，要么请求失败。原因见 debug 文档 4.5 节（hidden cache 的 block_size=8 把每 token 的 KV 成本放大到 4.576 MiB）。如果需要更长，告诉我，有一个已实现但默认关闭的开关可以放宽到约 7900 token，但它**需要先做改前改后的逐位对比验证**。

### 2.2 先抓 5 条试水

不要一上来就 200 条。先确认你的 token id 格式和服务配合正常：


把 `--input` 换成你的实际路径。检查产物：

```bash

```

manifest 每行长这样，这就是你要的**文件名与请求的对应关系**：

### 2.3 抓全量

试水通过就放开。`--concurrency` **不要超过服务的 `--max-num-seqs`**（当前 4）：

```bash
cd /vllm-workspace/vllm-ascend && python3 my_docs/scripts/capture_dataset.py --input /opt/w00958190/data/samples.jsonl --out-dir /opt/w00958190/capture_dataset --concurrency 4 2>&1 | tee /opt/w00958190/log/capture_full.log
```

脚本特性：

- **断点续抓**：已在 manifest 里的样本自动跳过，中断后重跑即可继续。要重抓全部加 `--overwrite`
- **逐条校验**：每条都验 `token_ids` 一致、`T` 正确、无 NaN/Inf，失败的只报错不中断，最后汇总
- **进度与吞吐**：每 10 条打印一次 token/s 和累计磁盘

200 条 × 约 2000 token 预计 **14 GB 左右**，分钟级完成。

### 2.4 落盘格式（交给 SpecForge 侧转换器）

| 项 | 值 |
|---|---|
| 文件 | `<out-dir>/captures/<id>.safetensors`，一条样本一个文件 |
| 张量 `hidden_states` | `[T, 6, 2560]`，`bfloat16` |
| 张量 `token_ids` | `[T]`，int64 |
| 第二维的 6 个 id 顺序 | **升序** `[4, 16, 24, 36, 44, 48]` |
| 对应关系 | `<out-dir>/manifest.jsonl`，每行含 `id`、`file`、`num_tokens`、`shape` 及你原样带入的字段 |

**第二维顺序的依据**：`EagleModelMixin._set_aux_hidden_state_layers` 做 `tuple(sorted(set(layers)))`，与 SpecForge 的「按 `target_layer_ids` 升序拼接」一致。前 5 个（id 4/16/24/36/44）对应 SpecForge 的 tap `[3,15,23,35,43]`，第 6 个（id 48）是 `hyper_connection_mixer` 输出，即 `last_hidden_state`。

**转换到训练格式时注意**：训练端期望 `hidden_states [1, T, 12800]`（5 个 tap 拼接）和 `target_last_hidden_states [1, T, 2560]`。所以要把 `[T, 6, 2560]` 拆成前 5 个 reshape 成 `[1, T, 12800]`、第 6 个取 `[1, T, 2560]`。**不要把 `[T, 6, 2560]` 整体喂给读取端** —— 它遇到 4 维 hidden 会静默按流求平均（那是 DSV4 口径），会静默掉点。

## 第三步 剩余验收（可选，但建议做）

### 3.1 aux id 48 对比 `prompt_logprobs`

这一项需要**另起一个不带 capture connector 的服务**，所以要停现在的服务：

1. 从已抓的某条样本取 `token_ids` 和 id 48 的向量
2. 停 capture 服务，按操作手册 4.2 节起普通服务
3. 对同一 prompt 请求 `prompt_logprobs`
4. 用 `lm_head.weight`（BF16）乘 id 48 向量得 logits，比较 top-1 一致率与最大 logprob 差

这验证的是「id 48 确实是送进 `lm_head` 的那个张量」。代码里已有 self-check 做对象同一性断言，这一步是数值侧的独立交叉验证。要做的话告诉我，我写脚本。

### 3.2 TP 一致性

同一条样本用 TP8 和其他 TP（若显存放得下）分别抓，比较余弦相似度与最大差。当前 TP8 是唯一验证过的配置。

## 当前已知边界

- **样本最长 2304 token**（服务配置所限，原因见 debug 文档 4.5）
- **必须无 MTP + eager**：MTP 会触发 six-region 的 page 一致性检查；无 MTP 的 ACL Graph 需上游 vllm#58040
- **prefix caching 和 chunked prefill 必须关**：前者会让命中缓存的 token 不重新 forward、aux hidden 缺失；后者是保守选择（未验证其等价性）
- **TP8 是唯一验证过的拓扑**
- `chat_template.jinja` 中 `preserve_thinking` 的真实变量名**仍未确认** —— 它不影响本文档（直接发 token id），但影响你那边生成 token id 时的渲染口径：

```bash
grep -o "preserve[a-z_]*\|reasoning_effort\|enable_thinking\|thinking[a-z_]*" /opt/model/Qwen3.8-Flash-Next-w8a8-mtp/chat_template.jinja | sort -u | tee /opt/w00958190/log/chat_template_vars.log
```
